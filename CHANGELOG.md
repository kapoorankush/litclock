# Changelog

All notable changes to LitClock are documented here. Format loosely follows [Keep a Changelog](https://keepachangelog.com/) — dates are ISO 8601.

## [Unreleased]

### Changed
- **The PWA's Factory reset now clears the setup-WiFi key, which it had been keeping** (litclock-dev#660). litclock-dev#620 made that key permanent and rotated it in gift mode and `prepare-for-cloning.sh`, but not on the path `litclock-reset.service` runs for the PWA's **Factory reset** card: `reset-setup.sh --wipe-wifi --strict-env-wipe --poweroff --yes`. Because that wipes WiFi, the next power-on comes up in the setup hotspot — broadcasting `LitClock-Setup` with the PREVIOUS owner's key, permanently, surviving every reset the new owner later performed, while the card's own copy promised "Erases **everything** — all settings and WiFi". **v0.223.0 had no such leak**, because the key regenerated every provisioning cycle, so this was a regression litclock-dev#620 introduced rather than a pre-existing gap. **The discriminator is `--wipe-wifi`, not the power-off.** A hand-run `sudo reset-setup.sh --poweroff` does not wipe WiFi: the clock powers off, boots straight back onto its saved network, and never raises a hotspot at all — so there is no setup network for a stale key to protect, and rotating would strand the owner's phone for nothing. The bench QA doc tests precisely that as "same owner, moved house" and asserts the key is unchanged, and that behaviour is preserved. Keying the fix on `--poweroff` would have traded the leak for a regression against a deliberately QA'd path; keying it on `--wipe-wifi` lets both be right. Rotation is now one `rotate_hotspot_password_for_handoff` helper called from both arms so they cannot drift apart again. **`prepare-for-cloning.sh` now powers the Pi off when it finishes**, because deleting the key was not sufficient on its own: the same script re-enables `litclock-firstboot.service` and Step 1 removes `.setup-complete` — both correct, since a cloned card must run first-boot — so booting the prepared master even once re-minted a fresh permanent key that then rode every clone, silently, after the success banner had printed. litclock-dev#659 sharpens it: the prepared card's intended end state is indistinguishable from a brick, so power-cycling it "to check" is the realistic operator move and the one that resurrects the key. `--no-poweroff` opts out for CI and bench work, with a red warning in its place. Two parity fixes rode along: the gift-path survivor check now tests `-L` as well as `-e` (a dangling symlink is invisible to `-e`, so a failed unlink of one reported success), and it surfaces `rm`'s own diagnosis, since "Read-only file system" and "Operation not permitted" need opposite remedies. **The test that should have caught the leak could not fail**: its harness substituted a shell no-op for the whole block whenever gift mode was off, so it wrote the password file, executed nothing, and asserted the file still existed. It now runs the real terminal branch with the real flags, and every guard here — in both directions, including "must NOT rotate" — was verified by mutation.
- **The setup network's password is now fixed per device instead of changing every time the clock re-enters setup** (litclock-dev#620). `create_hotspot()` minted a fresh 8-character password on every provisioning cycle and persisted it nowhere, while the network name stayed `LitClock-Setup` — so any phone that had joined once held a saved entry whose credential no longer worked. The trap fires on the ordinary paths: a WiFi reset after moving house, or a power cut part-way through setup. **The two platforms fail very differently, and only one of them fails safely.** Measured on hardware with two phones and two cycles under the same SSID (2026-08-10): iOS silently retries the saved password, then says *"Incorrect password for LitClock-Setup"* and immediately offers an empty password field — recoverable in a tap. Android (OnePlus 6T) reported **"No Internet Access"**, never mentioned the password, never offered a field, and dropped back to the home network; scanning the setup QR did not override the saved entry either. **A later measurement contradicts all three of those Android claims** (2026-08-15, a different handset, same stale-credential condition): "Connection failed — Wrong password for LitClock-Setup", an offered "Change password", and a QR scan that connected on the first try. Android's WiFi error surfaces have changed materially across releases, so both readings are recorded rather than one replacing the other, and the strongest version of the original argument — that Android left no user-discoverable recovery short of Forget This Network — is treated as unproven. None of that changes the decision: a stable per-device password means a normal owner never reaches any of these screens, which is the right outcome however gracefully a given Android build degrades. The password is now read-or-created once from `/var/lib/litclock/hotspot-password` (0600, atomic write) and reused, so the name and the credential stay in lockstep. Persistence is best-effort by design: an unreadable, malformed or unwritable file regenerates and logs, because provisioning must never be blocked by its own bookkeeping, a symlink or FIFO planted at that path is refused rather than followed or blocked on, a pre-existing world-readable file is tightened to 0600 on read, and the write is fsynced so a power cut during provisioning cannot lose a password a phone has already saved. **Gift mode regenerates it**, and so does `prepare-for-cloning.sh` — without that, every SD card cloned from one prepared master would broadcast `LitClock-Setup` with the same permanent key. Both rotations fail closed rather than printing success on a read-only card. One related leak was closed at the same time: nmcli takes credentials as space-separated argv tokens, which the support-bundle redaction filter never matched (it required `PASSWORD=`), so sudo's command-audit line carried the PSK into persistent journald and out through the diagnostics bundle — harmless while the value expired each cycle, not harmless once it is permanent. **The password survives a plain factory reset and a WiFi reset deliberately** — the motivating user is the same person re-provisioning their own clock. **Gift mode regenerates it**, so a recipient starts with a fresh secret and the gifter keeps no working key to their setup network. One thing this does *not* buy, contrary to the original theory: phones do not silently rejoin the setup network on their own. Neither handset would leave a working home network for one with no internet, so the user still opens WiFi settings and taps deliberately — the change is that the tap now succeeds.
- **The quote corpus is licensed CC BY-NC-SA 4.0, and the repo no longer advertises itself as plain MIT.** `LICENSE` was bare MIT and the README carried a `License: MIT` badge, so GitHub labelled the whole repository MIT — but `image-gen/litclock_annotated.csv` derives from [JohannesNE/literature-clock](https://github.com/JohannesNE/literature-clock), which is CC BY-NC-SA 2.5, and the corpus and the images generated from it therefore cannot be MIT. Anyone taking the CSV on the strength of that badge was relying on a grant this project has no power to make. The derivative is now distributed under **CC BY-NC-SA 4.0** rather than 2.5, which section 4(b) of the 2.5 license expressly permits ("a later version of this License with the same License Elements as this License"); the three License Elements are unchanged, so no obligation moves. 4.0 is the better instrument for this material on two counts: it licenses **sui generis database rights**, which 2.5 does not mention at all and which is the operative right for a curated quote compilation in the EU and UK, and it reinstates a terminated license if the violation is cured within 30 days, where a 2.5 breach terminates automatically with no automatic reinstatement. Upstream's original database remains available under 2.5; this re-versioning covers only this project's derivative. The practical consequence, unchanged but now stated where a reader will actually find it: **NonCommercial is inherited, not chosen** — LitClock cannot be sold, as hardware, as pre-flashed SD cards, or as a paid app, while the corpus carries it. Giving clocks away stays fine. Code remains MIT, and the split is sound under 2.5's Collective Work clause: shipping the CSV beside MIT code does not subject the code to CC terms, because the code reads the data rather than adapting it. The generated images *are* adaptations and are covered. `LICENSE` now names the non-MIT paths, `NOTICE.md` documents the re-versioning and quotes the enabling clause, and the README badge, Credits and Disclaimer were corrected together — the Disclaimer still said "released under the MIT License", which is the exact overstatement being fixed.

### Removed
- **`scripts/install.sh` is deleted** (litclock-dev#547, #38). The retirement was announced in v0.222.0's README ("the flashed image is the only supported install path"); this finishes it. The installer had to make OS-level decisions — SPI overlays, sudoers drops, group membership — on a machine whose settings belong to the user, which is untestable in principle, and three defects shipped unnoticed because release QA only ever flashes images (`curl | bash` aborted at the first `read` and exited 0; a DIY first boot could never write `.setup-complete`; SPI was enabled in the pre-Bookworm `config.txt`, leaving the panel blank). Nothing executes the script — pi-gen's references are comments and `update.sh`'s are legacy cleanup for devices installed this way, which keep updating fine. The guards it anchored are re-anchored where their subject survives: pi-gen's package list is now pinned explicitly (deleting `wireless-tools` — whose absence silently unships the WiFi power-save mitigation — now fails a test), the sudoers validate-before-install ordering check moved to `update.sh`'s test, and the venv posture invariants now point at `pi-gen/stage3/01-setup-app` — the path that actually ships. One guard does not port yet: the deleted test file's dynamic every-unit-is-wired inventory check — its stronger replacement (derived pi-gen unit guards) lives in the development repo's expanded pi-gen test suite and arrives with that port (litclock-dev#547).

### Added
- **The clock can now render quotes on-device, from the corpus CSV.** A Python port of the PHP image generator (`src/quote_renderer.py`) reproduces the pre-rendered images glyph-for-glyph: 66,582 measurements and all 4,809 corpus rows verified exact against the original GD/FreeType pipeline, re-proven by a parity CI gate in the development repo on every corpus or renderer change. Runtime rendering ships **off by default** behind `LITCLOCK_RUNTIME_RENDER`, double-gated by an on-device validation marker that `tools/validate_measurement.py check --stamp` writes only after this exact device's font stack reproduces all 284,022 reference measurements — so the flag cannot enable an unproven environment. Fallback on any failure is right-time-only: freshly-rendered quote → pre-rendered PNG for this minute → plain time draw; never a stale frame, because on a clock a wrong time is worse than no quote. This is the foundation for editing quotes without a 4,800-image regeneration, and for future translated corpora.
- **Diagnostics now record which render tier painted each frame.** `render_mode` (`runtime` / `image` / `image-fallback` / `time-only`) appears in the status file, the diagnostics page, and the support-bundle copy text, so "runtime rendering is off" and "runtime rendering is failing every minute and silently falling back" are distinguishable from a support bundle. A structural test asserts every diagnostics field is actually rendered in at least one human-readable surface.

### Changed
- **Nothing a recipient reads says "hotspot" anymore** (litclock-dev#581). "Hotspot" is infrastructure vocabulary — recipients read it as something they must own or configure. Every recipient-facing surface (the e-ink setup and retry screens, the setup page, the control app's System tab, the boot console, README and setup docs) now says what a phone user actually sees: a WiFi network named "LitClock-Setup". Internal names (units, functions, logs) deliberately keep `hotspot` — renaming working plumbing risks regressions for zero reader benefit.
- **The e-ink setup splash is written for a non-technical phone user** (litclock-dev#588). Labels lead with whose network it is ("LitClock's WiFi network / password"), a framing line under the QR says what scanning it does, and both fallback URLs carry the explicit `http://` scheme so typing them into a browser works verbatim. Same 43-character line budget, so nothing re-wraps.
- **The top strip is now a typeset masthead.** The date and the LOW temperature line stand on a shared baseline placed so worst-case descenders clear the horizontal rule by the same tightness the quote's ascenders keep below it; the weather cell is a centered icon-plus-temperatures lockup whose slot is sized programmatically over every temperature the formatter can emit, so no accepted value can overflow or shift the layout. Malformed weather data suppresses the weather cell instead of drawing garbage. `example.png` regenerated to show the new layout.
- **Bolding is now exactly the annotated time phrase.** The renderer previously extended bold through trailing punctuation and to word boundaries around the matched timestring; on some quotes that bolded a stray period or half a word. The corpus CSV's timestring column is now the bold spec, byte for byte — what the annotator marked is what bolds. 4,693 rows are pixel-identical, 116 gained a font size from reclaimed width, 0 regressed. `image-gen/generate_images.py` (whole-word bolding) is deprecated with a refuse-to-run guard; CONTRIBUTING documents the bolding contract for corpus editors and future translators.
- **The setup WiFi picker no longer arrives with a network already chosen** (litclock-dev#554). The dropdown had no placeholder, so the browser displayed its first option — and what sorted first was whatever order `nmcli` happened to return, which nothing in our code set and no test asserted. A recipient who tapped Submit without opening the dropdown submitted a network they never picked, plausibly a neighbour's, and got a WiFi-join failure they had no way to diagnose on a device with no keyboard. The list now leads with a disabled "Choose your WiFi network" placeholder, the `<select>` is `required` so the no-JS path refuses an empty submit before a slow captive-portal round trip, and the sort is ours: signal descending, ties in scan order. **Hidden networks can now be joined**, which was previously impossible through setup at all — a "My network isn't listed" option paired with a `<details>` text field (open-able without JavaScript, since captive-portal WebViews often have it off), passing `hidden yes` to nmcli so the client actively probes for an SSID no beacon advertises. The typed name gets the same own-network rejection as a picked one (case-insensitively — the page displays the setup network's name right above that field), is rejected outright if it carries control characters, and is capped at 32 **bytes**. `hidden yes` is asked for only when the radio genuinely cannot see the network: nmcli writes it into the *saved* profile, so a hand-typed but visible network would otherwise make the clock announce its owner's SSID in cleartext probe requests for the life of the install. Three more fixes landed alongside, from review: the Refresh button no longer disables the dropdown (a disabled control is excluded from the form data set **and** skipped by `required`, so a submit landing mid-refresh silently posted no network at all); the scan fetch is bounded by a 20s abort, so a dropped phone-to-clock link can't leave the picker reading "Scanning…" forever inside a WebView with no reload control; and the retry page echoes back the name you typed instead of making you remember it. Separately, the WiFi password is now redacted from the nmcli debug log — journald ships persistent on the flashed image and the support bundle collects it.
- **A WiFi join that hangs now fails in seconds, with an honest message** (litclock-dev#598). Joining a typed hidden network could leave nmcli hung ~107 seconds inside NetworkManager's activation — measured on hardware — with the setup hotspot already torn down (single radio), the phone dumped off the setup network with zero feedback, and the eventual error blaming the spelling. The connect is now bounded at 30 seconds; on expiry the user is told the network "didn't answer in time — check that it's a 2.4GHz network and in range" (a hidden 5GHz-only network is invisible to the clock's 2.4GHz radio and fails exactly here; the spelling hint is demoted to last). Because killing the nmcli client does not stop NetworkManager's activation job, the timeout path explicitly deletes the half-created profile — verified, with a loud journal line if the delete fails — which is also what aborts the still-running activation; otherwise the profile would linger armed with a possibly-wrong password and auto-connect behind the next setup attempt's back. Before deleting, a short rescue window polls for a join that landed just after the bound: mesh and band-steering networks legitimately take 30-45 seconds to hand out an address, and without the rescue such a network would be torn down mid-success and re-fail identically on every retry, forever. The manual CLI (`wifi_provision.py connect`) gains `--timeout` (0 = wait indefinitely, no auto-delete) so an operator recovering a clock over SSH isn't subject to setup-flow semantics that could delete the very profile they rely on.

### Fixed
- **A clock that cannot get an IP address no longer repaints the panel on every retry** (litclock-dev#667). litclock-dev#645 taught the NetworkManager dispatcher to treat a `169.254.x` self-assigned address as no address at all, so it could not mute the missing-IP fault — correct, but it blanked the variable the same-IP short-circuit is gated on. A blanked address failed that gate, never reached the early exit, and fell through to a full e-ink render, so **every** `dhcp4-change` reaching the dispatcher without a usable address queued another `litclock.service` start: three renders measured for three identical events where a real address produces one. That is precisely the unbounded-render failure the #309 review guard was written to prevent — each render holds the SPI bus, blocks the legitimate minute-tick paint, and spends panel cycles a device with no UPS and a finite budget cannot get back. **The same hole was open one branch over**: when the interface has no IPv4 at all the address is empty rather than blanked, and it repainted on all four of four events measured in the test harness. **Bench QA afterwards showed both branches are narrower in the field than that framing suggests** — see the reachability note at the end of this entry. The fix separates two questions that had been sharing one variable: *have I already acted on this address* (the observed value, kept before blanking, in its own tmpfs marker) and *what address should diagnostics believe* (the blanked value, still the only thing written where `read_lan_ip` can see it). Every repeat now coalesces — real, link-local, or nothing at all — while the first event after losing **or regaining** a routable address still repaints, because in both directions the panel is showing a QR that no longer matches reality. Because that early exit now sits above the address write, it additionally proves the diagnostics marker already agrees before skipping: without that, a plain file planted at the coalescing path in the pi-writable `/run/litclock` could suppress the write for the life of the boot and resurrect litclock-dev#645's false "Connection issue" with every symlink guard intact, and an ordinary deletion of the marker would never self-heal. Three smaller defects in the same file went with it: the change log line read `wlan0 IP changed to unknown (was: none)` on a blanked event while the marker still held the real prior address — a line asserting a change that did not happen and reporting "none" for a value that exists, on a device where journald is the only diagnostic channel; `install -d -o pi -g pi` failed **wholesale** where the `mkdir -p` it replaced would still have created the directory, so on any install whose user is not literally `pi` the marker write silently no-opped for the whole boot; and the two run-dir creation sites had drifted apart, leaving the one that runs on a permanently-DHCP-broken clock — the only one that runs there — without the pi-ownership attempt at all. The guard that should have caught the render storm asserted only that the address was not recorded and never looked at whether anything rendered. **Reachability, established on hardware after the fix landed and recorded here rather than left to imply more than it should:** on a single-stack IPv4 network a DHCP failure produces *no dispatcher invocations at all* — NetworkManager cycles `ip-config → failed → disconnected → prepare` and never reaches `activated`, so no `up` event fires and `dhcp4-change` needs a lease that never exists. The link-local branch likewise does not arise on its own, since nothing here sets `ipv4.link-local` and NM's default is to fail IPv4 rather than self-assign. Both branches were reproduced only by forcing the interface state directly. The empty branch is genuinely reachable where `ipv4.may-fail=yes` (it is) **and** IPv6 works, letting a connection activate v6-only with no IPv4 — a dual-stack network with broken v4 DHCP. The fix is correct and the coalescing is verified on hardware for the reachable case; the render storm is simply rarer in the field than the harness measurements alone would suggest. A related gap the same pass found — the last-rendered-ip marker is never cleared, so a stale address mutes the missing-IP anomaly for the whole outage — is tracked as litclock-dev#672 and is pre-existing, not introduced here.
- **The "do NOT clone this card" warning can now actually print** (litclock-dev#649). `prepare-for-cloning.sh` removes the per-device setup-WiFi password before an SD card is duplicated — the most safety-critical step in the file, because since litclock-dev#620 that password is permanent, so a card cloned with it intact would hand every recipient a network key the preparer knows. The step was guarded by a check that reports failure in red and tells the operator, in one sentence, exactly what not to do next. Under the script's `set -e`, a genuinely failing `rm` terminated the script **on the `rm` line**, so the check below it never ran and none of those three red lines ever printed. The warning written specifically to stop a key-reuse mistake was unreachable in exactly the situation it was written for. Hardware-verified by planting an undeletable file: the script exits 1 and never prints the success banner — so the literal requirement, "aborts rather than reporting success", was met — but the output ends mid-line at `Clearing setup-hotspot password... ` with nothing after it. An operator sees a truncated line and a stopped script, and is told nothing about the card in their hand. `chattr +i` is a contrived way to reproduce it; the realistic cause is a degrading SD card remounting read-only, or ownership drift on `/var/lib/litclock`, either of which lands at the exact moment someone is preparing cards to give away. The `rm` now takes the `|| true` that fifteen other calls in the same file already use for the same reason — the existence check that follows is the real gate, and the comment at line 68 had already spelled out the hazard verbatim. Testing needed the same correction: a test asserting the exit code passes with the bug present, since the exit code was never wrong. The new tests lift the real step out of the shipped script (verifying the span they lifted) and execute it against a temp directory with a forced removal failure, so the warning is asserted where it has to appear — on stdout, in the failure case. Review also caught that the check the step calls "the real gate" could miss a survivor: `-e` follows symlinks and is false for a dangling one, so a failed unlink of a dangling symlink at the password path reported success. The invariant is that no entry survives there — a surviving entry means the removal did not do what it claimed, whatever it points at — so the check now tests `-L` too. And since the point of the step is that the operator learns something actionable, `rm`'s own diagnosis is now surfaced instead of discarded — "Read-only file system" means the card is dying, "Operation not permitted" means ownership drift, and those need opposite remedies. **This does not make clone prep sufficient on its own**: the key also lives in a NetworkManager connection profile the optional WiFi wipe does not clear by default, and in persistent journald via sudo's command-audit line, both tracked separately (litclock-dev#653, litclock-dev#654).

### For contributors
- **`scripts/qa-reresolve-hw-test.sh` is tracked executable again, so an update stops dirtying the tree** (litclock-dev#682). `update.sh` Phase 6 runs `chmod +x` over `scripts/*.sh`, and this one file was tracked `100644`, so every update on every clock chmod'd it, left the tree dirty, and the **next** update then warned "uncommitted changes detected — will be overwritten by update", promised to overwrite them, and did not. Nothing broke; the cost is that the one line which should make an operator stop and look fired unconditionally on every device and was wrong every time, which is how a real warning gets trained out of usefulness. Observed on the fleet sentinel against v0.224.0. The mode was correct in the development repo all along and was lost in the port, so this is a repair of that port rather than a behaviour change — no file content is touched. A sweep of the other `chmod` targets found no second instance.
- **Contributions now state which license they arrive under, and corpus contributors get the translation caveat before they start.** The MIT/CC BY-NC-SA split left `CONTRIBUTING.md` — over 450 lines that walk a contributor through corpus editing in detail — without the word "license" anywhere, so "inbound = outbound" had more than one possible answer once the repo carried more than one outbound license. It now names three buckets: code, scripts, tests, configuration and documentation prose under MIT; the corpus, the `gold_set_192.csv` sample and the images generated from the corpus under CC BY-NC-SA 4.0; and bundled third-party assets (case STLs CC BY, weather icons CC BY-SA 4.0, fonts OFL-1.1) under the license they arrived with, so a contributor changing an STL is not silently assumed to be granting MIT. Opening a PR confirms the right to contribute and licenses the material to the project *and to everyone who receives the project* — CC BY-NC-SA 4.0 §2(a)(5) makes downstream recipients licensees of the contributor, not sublicensees of this project — while copyright itself stays with the contributor. The PR template carries the same terms as an acknowledgement, which is where a contributor actually looks. The caveat aimed at the waiting localization volunteers ([#19](https://github.com/kapoorankush/litclock/issues/19)): **a quote's copyright status is not the book's** — a translation is protected separately and usually owned by the translator *or their publisher*, so a public-domain novel does not put a modern translation of it into the public domain, and permission from a translator may not be theirs to give. A row from an old novel is a short excerpt of a long out-of-copyright work; a row from a modern translation is the whole of that translator's work on that passage. Also corrected: `NOTICE.md`'s quote-source table now lists the Guardian reader thread that README already credited, names the renamed upstream account (JohannesNE → JohsEnevoldsen, whose old raw URL 404s because GitHub does not redirect those — `gather_quotes.py` was silently skipping the source), and records arthurgassner/timeteller accurately as a **byte-identical mirror** of that upstream rather than an independent quote source.

## [v0.222.0] - 2026-07-23

### Fixed
- **Midnight quotes are attributed correctly again** (litclock-dev#584). The image generator seeded its bucket counter with the integer `0`, and PHP compares the `"0000"` time key to it numerically (`"0000" == 0` is true), so the first midnight row read as a repeat: midnight was numbered `quote_0000_1..72` instead of `0..71`, and because the corpus index is 0-based every midnight quote was captioned with the *next* row's author and title. Only `"0000"` collided, so midnight was the sole casualty. Fixed with a strict (`===`) compare and a `null` seed, pinned by a regression test; the ship pipeline now also sweeps orphaned PNGs a generator renumber can strand.
- **The settings QR now has its ISO 18004 quiet zone** (#25). The top-strip QR rendered flush against the divider line (no border — 2px of white above, 9px to the right), while the spec wants 4 modules (12px) of clear space on all sides; a Reddit report showed the divider running straight into the QR's bottom modules. The 78px strip can't hold a conventionally bordered QR, so the quiet zone is carved from the surroundings instead: the composite white-outs the strip's top-right corner and notches the divider under the QR before pasting, guaranteeing 12px left, right, and below by construction (the top edge rides the panel's physical inactive margin). Clearance verified against all 4,809 corpus images, with a new test that fails loudly if a future corpus regen inks the notch region. README hero photo refreshed to show the current layout.

## [v0.221.0] - 2026-07-18

### Security
- **Gift mode now forces SSH off before the device powers down** (#21). "Prepare for Gifting" wipes WiFi and resets config, but never touched SSH — so an owner who had ever enabled SSH would hand the recipient a device with SSH and the well-known default credentials listening the moment it joined the recipient's network. The gift flow now disables SSH across every vector (the `ssh.socket` unit that Bookworm socket-activates — disabling `ssh.service` alone left port 22 open, caught by on-hardware A/B testing — plus `ssh.service`, `raspi-config`, and the `/boot` re-enable flags) and verifies port 22 is actually closed before powering off, refusing to ship if it isn't. Recipients re-enable SSH from the console if they need it, same as a fresh flash.

### Fixed
- **A first-boot that times out now powers the device off instead of idling** (#22). When setup wasn't completed in the window, the e-ink painted "Setup Incomplete" and the Pi then sat powered on indefinitely — drawing current, holding the hotspot, reading as "stuck" on a shelf. It now paints the recovery instructions ("Unplug, then plug back in") and powers off immediately, with the message persisting on the bistable e-ink while off so the on-screen instruction and the device's actual state agree. A power cycle is the recovery.
- **iOS captive-portal probe handling hardened** (#20). Fixed a real hole where a probe to the bare `apple.com` host fell through to the full 20 KB setup form instead of the small bridge page. Apple detection probes now get a redirect off the Apple hostname (the pattern commercial portals use), the full documented Apple probe-host set is covered, and iCloud Private Relay / APNs traffic on the isolated hotspot is answered cleanly instead of being spoofed-then-refused. Note: extensive on-hardware investigation (including packet captures) established that current iOS (26.x) does **not** auto-open the captive sheet for offline setup hotspots regardless of the server's response — this is a client-side iOS change, not something the clock can fix. The documented "open your browser" fallback works every time and the e-ink instructs it; Android auto-opens as before.

### Changed
- **Release tooling: build-once, promote** (#23). The image workflow gained a promote path so a release can ship the exact image that was flash-tested, instead of rebuilding an untested image at tag time. Internal/CI only — no device-facing change.

## [v0.220.0] - 2026-07-15

### Fixed
- **The Control PWA can no longer crash-loop itself into a brick over the port-80 floor** (#15, #16). control_server binds port 80 as the non-root `pi` user, which needs `net.ipv4.ip_unprivileged_port_start<=80`. A field incident showed the persistent `/etc/sysctl.d` drop-in can silently fail to apply during an OTA (the install error was swallowed, and the update's only warning checked the live sysctl value, not the persisted file) — so the update reported success, the next reboot reverted the floor to 1024, and the service crash-looped on `EACCES` with no recovery path for a keyboard-less owner. Now `litclock-control.service` self-heals the floor with an `ExecStartPre` that re-asserts it as root on every start (idempotent, ~1ms), and `update.sh` verifies the drop-in by content and warns loudly (with the exact re-install command) if it is missing or stale. Reviewed by two independent adversarial passes.
- **Personalized gift welcome messages no longer get their tail cut off** (#17). The "Prepare for Gifting" welcome splash rendered the message at a fixed 48pt capped at two lines and ellipsis-truncated anything longer — "May it always be a good ti…" on a real gift. The splash now auto-fits: it shrinks the font down a `(size, lines)` ladder (48→44→38→32→28pt) and picks the largest size that shows the whole message with no ellipsis, only truncating a message far past the 280-character input cap. Short greetings still render at 48pt exactly as before.

### Fixed
- **A freshly provisioned clock no longer greets its new owner with a false "Connection issue"** (litclock-dev#645). Every clock coming out of first-boot showed **Something needs attention → Network: Connection issue** with a blank LAN IP in the PWA, starting about five minutes after setup and clearing only at the next DHCP renewal — up to an hour on a 7200s lease. Nothing was wrong with the device: `nmcli` had a valid address, and the e-ink handoff splash printed that address correctly on the same screen the owner had just scanned. Only the diagnostics view disagreed, because it does not ask NetworkManager — it reads `/run/litclock/last-rendered-ip`, which the NM dispatcher writes. The dispatcher was gated on `.handoff-complete` at the top of the script, above both of its bookkeeping writes, and the ordering on a fresh provision is fixed and always this way round: wlan0 comes up on the owner's network *before* the handoff marker is written, so the single `up` event that would have recorded the address was always the one skipped. The grey "Not yet collected" tier would normally mute a section with no data, but it requires an empty SSID on the reasoning that SSID-present-with-no-IP is a real DHCP failure — an inference that is wrong by construction here, since the collected marker sat behind the *same* gate while the SSID was populated. So the section rendered as a fault, and the 300s settling grace expired long before the marker could appear. The gate now sits immediately above the render it was written for: recording the current IP and refreshing the collected marker are inert bookkeeping and happen on every event, while `litclock.service` stays suppressed during hotspot teardown exactly as before. Events that changed something now say so in the journal instead of exiting silently — the silence is what let this sit unnoticed; a repeat event for an unchanged address stays quiet on purpose, since that is the common case and the journal is small. **Pre-existing, not a regression**; visible on every first run since the dispatcher shipped. **Suppressing a false alarm must not suppress a true one**, and un-gating the write opened exactly that door, so the dispatcher now refuses to record an address that would lie: its own setup hotspot gateway (wlan0 carries `10.42.0.1` during first-boot, and that is not the clock's LAN address), and a `169.254.x` link-local — the likely case, not the exotic one, since that is what NetworkManager self-assigns when DHCP fails on the owner's network. The anomaly check treats *any* non-empty value as a healthy network, so recording either would have meant a clock that never got a lease reporting itself fine, forever, on the very path this fix targets. The two QR producers already rejected those ranges before encoding a URL; the dispatcher was the one "LAN IP" producer that did not, and it is the one diagnostics reads. Also from review: the run directory is created with its ownership spelled out rather than a bare `mkdir` (root-owned `/run/litclock` would silently break every pi-side writer for the rest of that boot), and the previous address is read bounded and whitespace-stripped before being logged, because it lives in a pi-writable directory and is re-emitted by root — unbounded it could fail the log call large enough to abort the script before the render, and unstripped a planted newline could forge a standalone dispatcher line in the journal. Attribution now happens at the moment the marker changes state rather than at each caller, which makes a false claim structurally hard: every path names itself, a trigger arriving after the handoff already completed says so instead of taking credit, and the timer still reports honestly in both directions — it names itself when it genuinely completed the handoff, and says it fired and found the work done when it did not. ### Added

That's often too thin to actually debug a failing unit. Surfaced as a plain `<a download>` link beside the Copy button, so it works with no JavaScript.

- **LKG auto-revert: the clock now self-heals a bad over-the-air update without SSH or an SD reflash** (#209 follow-up). #209 shipped the *writer* (`litclock-lkg.service` records the last SHA that actually painted to `/var/lib/litclock/lkg-sha`, heartbeat-gated); this ships the *consumer*, `litclock-bootcheck.service`. It answers one question per boot — "did the clock paint a frame since this boot?" — via the tmpfs render heartbeat (network-independent, so a merely-offline clock is never touched). On a persistent failure it self-heals: fail 1 and 2 auto-reboot to retry (a single failed render may be transient), and on fail 3 it pins the last-known-good SHA and routes recovery **back through `update.sh`** in a new rollback mode, which does the *complete* install (git + submodules + venv hash-gate + units→`/etc` + sudoers + dispatcher + smoke) rather than a partial `git reset` — so a dependency- or unit-level bad update is actually recoverable, not just a code-only one. If the recovered code also fails it gives up (a persistent `bootcheck-gave-up` marker + best-effort "please re-flash" splash) instead of looping, bounding the whole sequence to ~4 reboots. Two supporting fixes make the recovery target reliable: `update.sh` **no longer clears `lkg-sha`** at the start of an update (the heartbeat-gated writer replaces it only once new code paints, so `lkg-sha` always points at the last code that actually rendered — a dead-on-arrival update can never blank the recovery target, closing the DOA gap), and a `blocked-sha` suppression stops the weekly timer from re-installing the exact release bootcheck just reverted from until a newer release supersedes it. Runs as `pi` using only the `systemctl reboot` + `systemctl start --no-block litclock-update.service` grants already in `sudoers/020_litclock-control` — no new privilege, works after #387 drops `010`. Hard prerequisite for #82 (public release: SSH is off, so a recipient's bricked clock would otherwise need a physical reflash). Design reshaped in `/plan-eng-review` + Codex outside-voice (plan: `docs/plans/lkg-bootcheck-plan.md`).

### Security
- **Closed the pi→root escalation paths so dropping the blanket `010_pi-nopasswd` sudo is safe** (#387, prerequisite for #82). Each was harmless while `010` grants `pi` NOPASSWD:ALL, but becomes a live hole the moment the public image ships with only the scoped `020_litclock-control` allowlist. **(tz-wrapper)** `geocoding.set_system_timezone` (the IP-geo + A18 browser-tz fallback) ran `sudo timedatectl set-timezone <arbitrary-tz>`, which `020` could only authorize via a `set-timezone *` glob — a hole letting `pi` set the clock to any string reaching the resolver. It now calls a new root-owned wrapper `/usr/local/lib/litclock/litclock-set-timezone` that re-validates the timezone against the kernel zoneinfo list *in root-owned code* (a metachar pre-filter + `grep -Fxq`, and `timedatectl` resolved via PATH — never an env-var binary override that could cross `sudo`); `020` authorizes just that fixed path. **(C1)** the root NetworkManager dispatcher invoked the **pi-writable** `/home/pi/litclock/scripts/litclock-mark-collected.sh` — pi→root on the next DHCP event once `010` drops. It now runs a root-owned copy in `/usr/local/lib/litclock/` (no fallback to the repo copy). **(prepare-for-gift)** `litclock-prepare-for-gift.service` (root, startable by `pi` via `020`) exec'd the **pi-writable** `reset-setup.sh` — pi could edit it and get arbitrary root code. It now execs a root-owned copy (with its sourced `lib/state.sh` shipped root-owned alongside), and the gift-message step runs the root-owned system `/usr/bin/python3` instead of the pi-writable venv interpreter. **(NTP grant)** `first-boot.sh`/`install.sh` run `sudo timedatectl set-ntp true`, which `020` didn't authorize — a fresh clock would silently never sync time once `010` drops; added as a fixed-argv grant. **(C2)** the dispatcher + mark-collected writer run as root but write into the `0755 pi pi` `/run/litclock` and `/var/lib/litclock` dirs; both now refuse to follow a symlink at the target and stage via `mktemp` (O_EXCL) instead of a guessable `$MARKER.tmp.$$` path. (A residual sub-millisecond check-then-open race remains — closing it fully needs an `O_NOFOLLOW` open POSIX `sh` can't express — accepted as an explicit risk: it requires an already-compromised `pi` shell winning a race for a limited-content root write.) All root-owned helpers install root:root across pi-gen, `install.sh`, and `update.sh`; the gift-mode `timedatectl set-timezone UTC` fixed-argv path is unchanged.

- **Diagnostics redaction now rounds compound-key and odd-shaped coordinates in the support-logs / journal export** (#497, #498). The diagnostics redaction rounds coordinates to ~city-block precision so the copy / support-logs / journal surfaces stay safe to paste into a public GitHub issue — but `_COORD_KEYED_RE` led with `\b`, which cannot match inside a compound key (the `_` before `LATITUDE` is a word char, so there is no boundary). systemd logs `env.sh` verbatim when a line uses `export` (`Ignoring invalid environment assignment 'export WEATHER_LATITUDE=33.1234'`), so the device's **full-precision, street-level home coordinates** rode un-rounded into the exported bundle while the structured field correctly showed the rounded `33.12`. The lead-in is now a zero-width negative lookbehind (`(?<![A-Za-z])`) — matching how the sibling `_PSK_RE` handles compound keys — which fixes the compound key, *also* catches back-to-back coordinates with no separator (a consuming lead-in would eat the boundary char, leaving nothing for the next coord's lead-in), and is safer against false positives (a *letter* before the keyword still blocks `belong=` / `along=` / `flat=` / `translation=`). The value group additionally rounds signed and scientific-notation spellings and JSON quoted-key forms (`{"lat": …}`); comma-decimals are deliberately left un-matched, since the `_validate_latitude` writer's `float()` rejects them (so they are unreachable) and a comma is ambiguous with a list separator (`lat=1,2,3` must never be fabricated into a coordinate). Found via a coordination-protocol pentest of the Control PWA (blind executor + blind validator, then a Codex adversarial `/review`); every non-plain-decimal shape was verified non-reachable in-tree, so the value-shape work is defense-in-depth. No incremental LAN exposure — the PWA is unauthenticated on the LAN by design and already serves coordinates rounded by default; the real fix is the share-safety contract (exported support-logs are meant to be safe to post publicly).

- **iOS captive portal now auto-opens on a fresh flash** (#483, #489). Fresh-flash test-Pi QA (with the #486 `CAPTIVE-PROBE` diagnostic in the image) pinned the real cause from the hotspot's dnsmasq log: iOS 17+ sends an HTTPS-RR (type 65) query for `captive.apple.com` before the A query (RFC 9460), and NetworkManager's shared-mode dnsmasq — which reads `/etc/resolv.conf` and inherits a public upstream like `8.8.8.8` — **forwarded** that type-65 query upstream. The isolated hotspot has no route to that upstream, so the forward failed and dnsmasq returned `REFUSED (EDE: network error)`, which iOS reads as hostile DNS and silently demotes the captive sheet (the exact failure #178 was chasing). The `local=/#/` mitigation never actually stopped the forward — it only looked fine on client Pis whose inherited upstream happened to be reachable and answered NODATA. The fix adds **`no-resolv`** to the captive dnsmasq config so it keeps no upstream at all and answers every non-A type authoritatively as NODATA; iOS falls through to the A record and pops the sheet. Manual "open in your browser" always worked (it only needs the A record), which had masked the DNS cause. Reproduced + fix-verified against a standalone dnsmasq 2.90 with an unreachable upstream (type-65 REFUSED → NODATA).
- **First-boot hardening for the captive-portal window** (#483, #488). Shipped alongside #489 from the same investigation; useful defense-in-depth even though the DNS forward above (not readiness) turned out to be the actual cause. (1) `first-boot.sh` now waits for the setup server to be listening on port 8080 (bash `/dev/tcp` poll, 25s cap, best-effort) **before** painting the hotspot QR, so the user's join always lands after the server can answer a probe. (2) The image build now **ships pre-compiled bytecode** for `src/` (`compileall --invalidation-mode checked-hash`, compiled with the runtime venv interpreter, then chowned to `pi`) instead of deleting all `__pycache__` in the finalize stage, so a fresh flash no longer compiles the setup path cold on its first run; `checked-hash` keeps the image reproducible and correct across `update.sh`. A cross-model `/review` caught that the compile runs as root after the build's `chown` (would have shipped root-owned `.pyc` the `pi` runtime couldn't refresh after an OTA) — closed with a re-chown.

### Security
- **control_server now sends `X-Content-Type-Options: nosniff` + `X-Frame-Options: DENY` on every response** (#477). Added off the back of a whole-codebase SAST + DAST pass (report: `docs/security-sast-dast-2026-07.md`), which found the code otherwise clean — 0 dependency CVEs (pip-audit + npm audit), no SSRF (fixed hosts, quoted queries), no command injection (fixed-argv `sudo`/`systemctl`; the diagnostics `unit` arg is allowlist-gated), and CSPRNG (`secrets`) for the WiFi hotspot password + CSRF + confirm tokens — but the PWA served no HTTP hardening headers. `nosniff` is universal defense-in-depth; `X-Frame-Options: DENY` closes a clickjacking vector, since the PWA is unauthenticated on the LAN and a malicious same-LAN page could otherwise iframe it and trick the owner into a state-changing control (Reset WiFi / power off). A content-security-policy is deferred to the remote-exposure tripwire (where auth + HTTPS + CSP all become required together).

### For contributors
- **`setup_server` background threads are now joined between tests, killing a `test_wifi_retry_flow` CI flake** (#478, #479, #480). The WiFi connect/teardown handlers spawn daemon threads (`_delayed` SIGTERM timer, `_connect_and_teardown`, `_resolve_and_signal`) that write module globals + call test-monkeypatched functions. `reset_state()` (the #355 isolation helper) previously only polled the `WIFI_CONNECT_IN_FLIGHT` flag — which `_delayed`/`_resolve_and_signal` never set — so a prior test's thread could outlive its case and fire its (now next-test-monkeypatched) `os.kill`/retry into the next test's counters (intermittent `assert 4 == 3` / `assert 1 == 0` failures in CI while passing in isolation). Regression tests assert on their own thread handle, not the shared registry count, so they can't re-introduce cross-test coupling. A post-merge cross-model `/review` of the first cut caught two latent races that the follow-up hardened.
- **Captive-portal probes now log Host + path + User-Agent in provisioning mode** (#483, #486). The setup server's access log recorded only the request line + status, which couldn't pin why an iOS phone's captive-portal sheet sometimes doesn't auto-open on join (observed in fresh-flash QA; tapping the browser manually always worked). Diagnostic only; no change to the captive-portal response flow. ### Fixed
- **Settings auto-save controls can no longer persist state opposite the UI under rapid taps** (#457, with the #458 helper convergence). All three auto-save controls (Weather toggle, Temperature pill, Advanced toggles) used to `abort()` the in-flight `fetch` on a re-tap — but an aborted request whose POST already reached the Pi still completed its `env.sh` write, and writes serialize on the flock by acquisition order, not send order, so an older save could land *after* a newer one and persist the opposite of what the toggle showed (until the next reload). The fix is client-side **serialization + coalescing**: each control now keeps at most one save in flight and coalesces rapid taps to the latest desired value, firing a single follow-up save only after the in-flight one settles. Because two saves for one control never overlap, the flock can't reorder them — persisted state always converges to the value the user landed on (a burst of N taps costs ≤2 round-trips). On failure the helper reverts to the last server-confirmed value and alerts. ### Fixed
- **PWA Settings Save no longer hangs indefinitely when a shell writer is stuck holding the env.sh lock** (#374, #274 follow-up). The shell-side env.sh writer-lock helpers in `scripts/lib/state.sh` honored a 30s `LITCLOCK_ENV_LOCK_WAIT` budget (timeout-and-skip via `flock -w 30 -E 75`), but the Python side in `src/config.py` called `fcntl.flock(LOCK_EX)` with no timeout — a stuck shell writer (wedged `mv` on a degraded SD card, `strace` left attached, kernel oops mid-rename) would block the Flask request thread forever and pile up stuck threads in waitress on every Save retry until OOM. `_exclusive_lock` now polls `LOCK_EX | LOCK_NB` with a 10ms cadence and raises `TimeoutError` on a 30s deadline (same `LITCLOCK_ENV_LOCK_WAIT` env-var as the shell side). - **`ENV_LOCK_WAIT_DEFAULT` module constant in `src/config.py`** — matches the shell-side `ENV_LOCK_WAIT_DEFAULT` budget and reads the same `LITCLOCK_ENV_LOCK_WAIT` env-var. The route was querying `systemctl show -p ActiveEnterTimestamp litclock-update.service`, but the PWA-triggered apply path doesn't reliably populate that property — so the row went silent in exactly the post-update moment the user most wants the trust signal. Now reads `/run/litclock/update.status`'s `finished_at_unix` + `to_version` (state=complete), falling back to `/var/lib/litclock/lkg-sha`'s mtime + sha7 across reboots; renders em-dash only when neither file exists (true first-run state).

### For contributors
- **Python deps now use a `pip-compile`'d lockfile** (#323). `requirements.in` is the human-edited source of truth for direct pins; `requirements.txt` is the **generated** lockfile with every transitive (werkzeug, click, itsdangerous, blinker, markupsafe, cffi, pycparser, h3, flatbuffers, numpy) explicitly pinned. Closes the eager-strategy gap from #321: PR #322 narrowed `update.sh` to plain `--upgrade` (no eager) to avoid silent fleet-wide transitive bumps killing Flask, but that left transitive security fixes unreachable. The lock-at-release-cut workflow restores deterministic install AND a controlled bump path — maintainer runs `pip-compile --upgrade requirements.in` locally, reviews diff, tests on a Pi, tags release. All 8 existing `requirements.txt` readers (update.sh, install.sh, pi-gen, lint.yml, 3 tests, README/CONTRIBUTING) keep working unchanged — same filename, same `name==version` line format. `requirements-apt.txt` filter still strips the 5 apt-provisioned names (gpiozero/lgpio/spidev/pigpio/colorzero) at install time. See CONTRIBUTING.md → "Updating Python dependencies" for the full workflow.
- **`MAX_RELEASE_NOTES_BYTES = 4096`** in `update_state.py` caps `release_notes` before `write_cache` so the cached JSON stays under `MAX_GH_API_CACHE_BYTES`. Without the cap, a verbose CHANGELOG could exceed the read-side limit and cause `/api/update/check` to refetch GitHub on every request, burning the PAT rate budget. **Important pairing:** `write_cache` now uses `json.dump(..., ensure_ascii=False)` — the default ASCII escaping inflates each non-ASCII codepoint to `\uXXXX` (6 bytes), so a 4KB emoji-heavy notes section would otherwise serialise to ~12KB and trip the read gate. Pattern: if you ever cap a string by UTF-8 byte length, the writer that produces the consuming file MUST also write UTF-8 (not ASCII-escaped) for the cap to be meaningful.
- **`scripts/update.sh` persist function now sweeps orphan `.tmp.*` siblings** on entry (#342 I4). Mirrors the manifest-sweep pattern from PR #293. Defensive: if a prior persist died between staging and mv (disk full, OOM, kill -9), the .tmp.\<pid\> sibling lingered indefinitely.
- **`ConfirmTokenStore.restore()` now clamps `expires_at_monotonic` to `<= now + TTL_SECONDS`** (#342 I8). Defense-in-depth — today's callers always round-trip the expiry from `consume()` so the clamp is a no-op on the happy path. A future refactor that synthesises an expiry (e.g. hardcoding `now + 86400`) can no longer silently mint a long-lived token bypassing the 300s TTL contract.
- **`prepare_for_gift`'s `CalledProcessError` branch narrows the staged-message unlink to `returncode in (4, 5)`** (#342 I9). Per `man systemctl(1)`: 4 = unit not found (the #327 install-gap motivation), 5 = unit not loaded / masked. Other returncodes preserve the staged message so the unit can read it if it dispatched anyway (the narrow dbus-glitch window the existing comments already acknowledged for the token-restore path). The original unconditional unlink risked silently replacing a user's personalized welcome with the default splash on the rare dispatch-but-non-zero-exit race.
- New shared `safe_read_json` / `safe_read_text` helpers in `src/control_server/update_state.py` close a TOCTOU window when reading state files. Pattern: `os.open(path, O_RDONLY | O_NOFOLLOW | O_CLOEXEC | O_NONBLOCK)` → `fstat` the resulting FD → `S_ISREG` + size check → `read`. The `O_NONBLOCK` matters specifically for FIFO defense — without it, `open()` on a malicious FIFO hangs the worker thread, defeating the hardening. Use these helpers (not raw `Path.stat()` + `open()`) for any new defensive file-read in the project.
- `scripts/update.sh` now wraps its body in `flock -n -E 75 /var/lib/litclock/update.lock` so concurrent manual invocations exit cleanly with a clear message instead of racing on the state files. Best-effort fallback when the lock file can't be created (sandbox/CI environments where `/var/lib/litclock` doesn't yet exist) logs `log_warn` so the journal records the degraded mode.
- `ConfirmTokenStore.consume()` signature changed from `-> bool` to `-> float | None` (returns the original monotonic expiry on success). New `restore(action, token, expires_at_monotonic)` method atomically re-adds the token; route handlers call it on any pre-side-effect failure path. `TimeoutExpired` deliberately does NOT restore (paranoid: systemd may have dispatched).
- `_validate_latitude` / `_validate_longitude` now accept empty string as a valid "unset" state — required for the Clear weather path to work. Routes enforce all-or-none across the three weather location keys at the API layer to prevent incoherent partial-coord saves via direct JSON callers.
- `create_app` defaults now seed `UPDATE_STATUS_FILE`, `LAST_UPDATE_FILE`, and `LKG_SHA_FILE` from their `LITCLOCK_*_FILE` env vars at app-creation time, matching the existing `ENV_FILE` pattern. Future tests using `app.config[...] = tmp_path` see consistent behavior; future tests that set env vars after import no longer silently use production paths.
- `.settings-button--secondary` now matches DESIGN.md "Buttons" Secondary spec (transparent bg + `--accent` text + `--accent` border, hover/active to `--accent-muted`). Prior implementation read as a disabled grey chip and didn't map to any DESIGN.md variant. All future non-destructive secondary actions in Settings should reuse this class.
- All `CalledProcessError` branches in the 5 destructive route handlers (reboot, poweroff, prepare_for_gift, update_apply, wifi_reset) now carry an inline comment acknowledging the residual dbus-race dispatch window. Future destructive actions that are NOT idempotent at the systemd level must narrow the restore to specific pre-dispatch stderr patterns or remove the restore for that action.

### Heads-up — weekly auto-update behavior (#209)

LitClock now updates itself automatically **once a week on Sunday at 03:00 local time** (with up to 7 days of randomization to avoid everyone hitting GitHub at once). The appliance posture is deliberate: non-technical users should never have to think about updates, and power users can opt out in one command.

**What the weekly update does:**
- Pulls the latest blessed GitHub Release (`litclock-*` tag), not `origin/master`. A release is only cut once a SHA has been hardware-verified.
- Rebuilds the Python venv when `requirements.txt` changes.
- Runs a post-rebuild **smoke test** (`python -m src.literary_clock --dry-run`). If the render fails, the update auto-reverts to the previous SHA and the clock keeps ticking on the old code.
- Records a last-known-good SHA to `/var/lib/litclock/lkg-sha` after the clock has run 10 minutes on the new code (observability today; an opt-in auto-revert on repeated boot failures is a future issue).
- Merges new env-var names from `env.sh.sample` into your `env.sh` without overwriting your values.

**What does NOT update automatically:**
- OS packages (`apt upgrade`), Pi firmware — those need A/B partitioning we don't have yet.

**How to opt out:**
```bash
sudo systemctl disable --now litclock-update.timer
```

**How to inspect:**
```bash
systemctl status litclock-update.timer
journalctl -u litclock-update.service --since "1 week ago"
```

See the [Updating](README.md#updating) section of the README for the full story. Refs #209.
