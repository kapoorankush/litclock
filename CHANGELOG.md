- **Stage-4 translation content gates** (litclock-dev#757) — the Stage-3 gates prove key-set parity; these prove VALUE conformance, so the first translated bundle (Spanish) is linted the moment it lands in the registry rather than on activation day. Every registry language is checked for: placeholder parity by OCCURRENCE COUNT (the /review caught that four templates split-render a slot exactly once, so a set-based check would pass a duplicating translation that then truncates its tail); rich-token (`{b}`/`{em}`/`{code}`) balance and nesting against a per-key vocabulary source-scanned from the `t_rich`/`_rich` call sites and pinned against the production resolvers (a resolver-side vocab shrink fails loud); and a content lint — raw `<`/`>` (kills raw tags and a `</script>` inside a json.dumps'd inline-JS literal; the accepted false positive on "Settings > WiFi" is documented), HTML entities, stray-brace residue, brace confusables (`｛｝`), bidi overrides, control characters except `\n`, and invisible-only values (a zero-width space survives `strip()`). - **Booting with WiFi already saved no longer serves a setup page — setup completes by itself** (litclock-dev#647). - **A factory reset now erases both saved passwords — your WiFi and the setup network's** (litclock-dev#666, litclock-dev#664; owner decision). The old rule rotated the setup-hotspot key only when the WiFi was wiped **and** the device powered off. That pairing was carefully reasoned and still too clever: which of the four flag combinations you happened to use decided whether the previous owner kept a working, permanent key to the next owner's setup network. The rule is now the one people mean when they say factory reset — both passwords go — so `--wipe-wifi` becomes the default and rotation is gated on it alone. That also closes a gap the old shape left open: a reset that **rebooted**, or one that just finished and left you to power-cycle, raised the same setup hotspot on the next boot carrying the old key, because only the power-off arm rotated. Which exit a reset happens to take is not something a credential's lifetime should depend on. **`--keep-wifi` is the single opt-out, and it is command-line only.** It preserves both, which is coherent rather than a special case: if the WiFi survives, the clock returns to its own network and never raises a setup hotspot, so there is no setup network for a rotated key to protect and rotating would strand the owner's phone for nothing — that is the old "same owner, moved house" path, now reached deliberately by a flag instead of by accident through a flag combination. It is also what keeps an SSH session alive through a reset. Someone typing it into a shell has self-identified as technical; the PWA has no way to express it and a test pins that it never acquires one, because the tapped path is the one a non-technical owner uses to hand the clock on and it must never quietly become the lenient one. The user-facing copy was updated to match, which was the actual complaint in litclock-dev#666: the confirm modal, the in-progress screen and the README all told the owner to rejoin `LitClock-Setup` from their phone's WiFi list, on a path that had just invalidated that saved credential. They now say the password will be new, that it is shown on the clock's screen, and that a phone holding the old one must forget the network first.
- **The setup network's password is now drawn from an alphabet you can actually read off the screen** (litclock-dev#670). The generator used all 62 alphanumerics, which contains every classic transcription pair: `O`/`0`, `l`/`I`/`1`, `S`/`5`, `B`/`8`, `Z`/`2`. That is the wrong alphabet for a value whose entire job is to be read off a 1-bit e-ink panel and retyped into a phone. The evidence is as direct as it gets: the project's own author, reading his own screenshot of `cz7yOjWA`, could not tell whether it held a capital O or a zero. By the arithmetic 1 - (49/62)<sup>8</sup> = 84.8% of 8-character draws contained at least one of the excluded characters, and 4 of the 4 generated during the v0.224.0 bench pass were ambiguous. litclock-dev#620 is what turned that from an annoyance into a defect: before it, an unlucky draw was replaced at the next provisioning cycle, so the ambiguity was transient; now a device that mints an ambiguous key re-presents that exact string at every future setup for the life of the device, and a recipient who mistypes it lands on the litclock-dev#648 "Wrong password" screen — or, on the Android behaviour litclock-dev#620 measured, a dead end that blames the router. litclock-dev#588 had already rewritten the splash prose for readers who had never joined a device's own network; it fixed the words and left the characters. The alphabet is now derived by excluding the confusion classes rather than written out, so the exclusion is checkable in both directions, and one member of a class is kept where it is unambiguous alone (lowercase `b` and `z` survive because `B`/`8` and `Z`/`2` are gone). **The key is now nine characters, not eight, and the reason is the salt.** Narrowing the alphabet costs entropy: 49<sup>8</sup> is 44.9 bits against the 62<sup>8</sup> = 47.6 the fleet had before. Eight would have been defensible on the old reasoning — the AP is LAN-local, up for minutes during setup, and the binding exposure has always been that the key is printed on the panel in plaintext by design. What changed it is a fleet-wide fact rather than a per-device one: WPA2-PSK derives the PMK with PBKDF2-SHA1/4096 using the **SSID as the salt**, and `DEFAULT_SSID` is a build-time constant identical on every LitClock — so the salt is fleet-constant, a precomputed table is reusable against every device ever shipped, and the marginal cost of the second device is about zero. litclock-dev#620 then removed the rotation that used to bound a bad outcome in time. Nine characters gives 49<sup>9</sup> = **50.5 bits, more than the fleet had before any of this**, for one extra character to type — so the legibility fix costs no margin. The floor the tests assert is the pre-dev#670 47.6-bit baseline, not a number derived from the two constants, so a silent revert to eight fails. Verified on the panel too: the worst possible nine-character draw (the widest glyph in the alphabet, repeated) measures 213px against a 510px column budget, so the renderer's ellipsis clamp is a no-op — an ellipsised password would not be a cosmetic bug, it would be unjoinable. Existing devices are untouched: litclock-dev#620 made the stored password permanent, so this changes what new devices mint, not what provisioned ones present. Verified by rendering the real splash: every character of the new alphabet was checked on an actual 800x480 1-bit frame, not reasoned about.
- **The setup page no longer opens with the keyboard over the form** (litclock-dev#671). The WiFi password field carried `autofocus`, so focus landed on step 2 of a form whose step 1 is the network picker. On a phone that pops the keyboard immediately, covering the lower half of the page, before the user has touched the control the page leads with. Observed on both the iOS and Android captive portals during the v0.224.0 RC bench pass. Nothing could be mis-submitted — the `<select>` has been `required` since litclock-dev#554, so an empty submit is refused client-side before any round trip — but the focus order still steered people into the wrong first move: type the password, tap Submit, get a validation bubble anchored to a picker that may now be behind the keyboard, with nothing on screen explaining the order they were supposed to work in. That is the same failure litclock-dev#554 set out to fix, arrived at from the other side; `required` fixed the data half and left the sequencing half. `autofocus` is simply dropped, so the page opens on its own heading and picker. It is deliberately **not** moved to the `<select>`: on mobile that can spring the native picker wheel open on load, which is louder than what it replaces, and captive-portal WebViews differ again — a test now fails if `autofocus` reappears on any control in the form, or if a script focuses the password field instead, so putting it on the picker is a decision that has to be made with two phones in hand.
- **Diagnostics no longer reports a network fault on a clock whose WiFi has been stable** (litclock-dev#552). The Network section showed the orange "Connection issue" on any device whose DHCP lease was more than 24 hours old — so the longer the network worked perfectly, the more confidently the page reported a problem. The NetworkManager dispatcher short-circuits on an unchanged IP, which freezes `last_dhcp_at` at boot, making lease age a measure of stability rather than reachability. On the affected clock every direct signal was healthy (−37 dBm, IP present, `nmcli CONNECTIVITY full`) and the 291-hour-old timestamp was the sole complaint. `Last DHCP` remains a displayed row — it is useful when debugging; it just no longer raises an alarm. That is the misattribution failure litclock-dev#648 was filed about, arriving by a different route. #22 also closes litclock-dev#529, which is CLOSED here while the code that closed it lived only on public: an issue being closed on dev does not imply the fix is in the dev tree, and that is exactly how this stayed invisible. The other half is a **field incident** (litclock-dev#527): a silently-swallowed sysctl drop-in install let `sysctl -w` set the live port floor to 80, so the update reported success and the next reboot reverted to 1024 and crash-looped control_server. `update.sh` now verifies the persisted drop-in against the shipped file with `cmp -s` — content, not mere existence, since a stale drop-in whose overwrite failed passes a `-f` check while being wrong — and `litclock-control.service` carries an `ExecStartPre=+-` sysctl self-heal so a keyboard-less owner is not left in an EACCES loop. Ported per file, never wholesale in either direction: public's 8-character hotspot password predates litclock-dev#670's nine, so a bulk sync would destroy real work going the other way. (This entry also said public carried a litclock-dev#528 SSH-off gate that dev deliberately did not — true when it was written, and no longer: litclock-dev#657 brought that gate here and then removed the dev exception entirely. See the Security entry below.) **Two behaviours are dev-only and deliberate,** so the next port outward carries them: the splash suppression is gated on the recovery copy having actually painted (an unpainted panel plus a muted splash powers the device off still showing the stale hotspot QR — an SSID and password nobody can join), and the power-off has the loud fallback dev already gave the same call in `prepare-for-cloning.sh`, clearing the marker so a failed shutdown does not go on muting every later one. Also recorded rather than silently traded away: `sudo touch /run/litclock-splash-suppress` is **not** in the scoped 020 allowlist and must not be added — that would let a pi-level process mute the gift welcome, which the root-owned path exists to prevent — so the marker stops working if the broad 010 grant is ever dropped, and a test pins both halves of that statement. Twenty-one mutants killed. Several were holes in the tests as public wrote them: deleting `sudo systemctl poweroff` stayed green because the rationale comment names it verbatim, and the unit assertion was satisfied by a comment (so `=8080`, which raises the floor above 80 and reproduces the crash-loop, passed). The port also first hand-rolled a replacement for #15's unit test on the false belief that public shipped none — it did, in `test_systemd_units.py`, and leaving dev without it would have made the next dev→public port delete public's copy.
- **A factory reset that fails now tells someone, instead of only the journal** (litclock-dev#665). litclock-dev#660 made the reset fail closed, which is right — but on the PWA path there is nobody to tell. `routes/system.py` dispatches the unit with `systemctl start --no-block` and returns 200 immediately, and `static/js/system.js` deliberately never polls, rendering a terminal "Factory reset in progress…" card. So a rotation that failed on a read-only remount left the red "do NOT pass this device on" banner in a journal nobody reads, the card spinning forever, and an owner who eventually pulls the plug — after which the next boot raises the setup hotspot with the **old key**, which is precisely the outcome the fail-closed guard exists to prevent. Gift mode has had the same shape since litclock-dev#393, but gift mode has an operator at a terminal watching the output; the PWA path has neither.
  `litclock-reset.service` now carries `OnFailure=litclock-reset-failed.service`, which writes a persistent marker and then paints the e-ink — the one output surface that survives a frozen PWA. **Both** commands are `-` prefixed, and review is what made that necessary: a non-dashed `ExecStart` that fails aborts the remaining ones, so an undashed marker write meant a read-only `/var/lib` would stop the splash from ever running — and a read-only remount is the most likely reason the reset failed in the first place. The guard would have gone silent in precisely the scenario it exists for. Neither half may block the other. The announcer also runs as **pi, not root**: `/var/lib/litclock` is `0755 pi pi`, so a root unit redirecting into it could be made to follow a symlink pi had pre-placed, and the splash execs a pi-writable script and venv — a pi→root escalation on both halves, of exactly the class this repo already closed in `litclock-prepare-for-gift.service`. Nothing here needs root: `litclock-bootcheck.service` paints the same panel as pi. The splash says what the owner actually needs to know rather than that something went wrong: the clock may still hold its previous owner's settings, do not pass it on, power-cycle and try again. The announcer is deliberately **not** enabled and has no `[Install]` section; systemd starts it exactly when the reset unit fails, and an enabled copy would announce a failure that never happened on every ordinary boot. Two limits are worth stating rather than leaving to be discovered: `OnFailure=` does **not** fire for an unmet `Condition*=` (systemd records those as skipped, not failed) nor for a stop ordered by the `Conflicts=litclock-update.service` interlock, which goes inactive rather than failed — that interlock's half-wiped outcome is a separate problem and is not fixed here. And the marker has no reader yet: it is written for the e-ink's benefit and for an operator with a shell, not consumed by /diagnostics or the PWA. `reset-setup.sh` clears it at the start of every attempt, and verifies the removal rather than trusting `rm -f`'s exit code, so it means "the most recent attempt failed" rather than "one failed once, ever" — the stale-marker class litclock-dev#672 was about. Clone prep clears it too, so a cloned card never tells its recipient not to pass on a device that is fine.
- **/diagnostics no longer reports a healthy network for a clock that has lost its address** (litclock-dev#672). Nothing has ever cleared `/run/litclock/last-rendered-ip`, and the Network section was served straight from it, so a clock that loses DHCP *without rebooting* kept showing its pre-outage address for as long as it stayed up. Confirmed on hardware during the v0.224.0 bench pass: DHCP blocked at the device, `wlan0` holding no IPv4 for about four minutes, and every sample reading `wlan0=[] observed=[192.168.2.99] rendered=[192.168.2.99]`. `_compute_anomalies` only tests `lan_ip` for truthiness, so the 300-second settling grace never even came into play — the value was not missing, it was **stale**. That is the exact user-visible failure litclock-dev#645 was opened to fix, reached from the other direction: litclock-dev#645 and litclock-dev#667 both took care not to *write* an unbelievable address, and neither could do anything about the believable one already there. Worse than the state before litclock-dev#645, which at least showed a visibly wrong `169.254.x` on some configurations; this showed a plausible, wrong, stale home-subnet address.
  A fix routed through the dispatcher could not have worked, and the same bench pass is what established that: on a single-stack IPv4 network a DHCP failure produces **zero** dispatcher invocations — NetworkManager goes `ip-config → failed → disconnected → prepare` and never reaches `activated`, so no `up` fires and `dhcp4-change` needs a lease that never exists. The marker goes stale precisely because nothing is running to update it. So the read side stops trusting it: the interface's current address is now consulted first and is **authoritative when it can answer**, including when the answer is "there isn't one" — which is what trips the anomaly. The marker is used only when the live read could not run at all — a missing binary or a timeout, which `cached_subprocess` reports as `None` rather than `""`. Falling back on an authoritative negative would restore exactly the muting this fixes, and a test pins the distinction in all three directions. One honest limitation: `cached_subprocess` collapses *any* non-zero exit to `""` without surfacing the code, so an `ip` that runs and fails reads as "no address" rather than as "could not observe". Of the two ways to be wrong that is the one which surfaces a fault instead of hiding one, which is the call `_anomalies` makes everywhere else — and a genuinely broken `ip` is a real problem. It is pinned by a test so the choice is visible rather than accidental.
  The read is **scoped to the default-route interface**, and that is load-bearing rather than tidiness. An un-scoped read takes the first global IPv4 by interface index, so a second global-scope interface — `docker0`, `wg0`, `tailscale0`, a `usb0` gadget, a USB-ethernet dongle — re-opens the exact muting this closes: demonstrated with `wlan0` holding no IPv4 and `docker0` up, /diagnostics reported `172.17.0.1` and the network anomaly did not fire. It also defeats the hotspot exclusion, because skipping `10.42.0.1` on `wlan0` simply falls through to the next interface. The dispatcher that writes the marker is interface-scoped for the same reason and says so in a comment about a later USB dongle grabbing a different name, so scoping here is also what keeps the two agreeing.
  `ip addr` rather than the connect-trick `literary_clock` uses for the QR, deliberately: that opens a UDP socket toward a routable address and reads back the egress IP, so it returns nothing on a box that **has** an address but no default route. For the QR that is correct — an unreachable clock should fall back to mDNS — but here it would report "no IP" for a device that is serving the very page making the claim, which is the false-positive class `_compute_anomalies` already carries a warning about. The live read also refuses the same three addresses the dispatcher refuses to record (loopback, a DHCP-failure `169.254.x`, and our own setup hotspot's `10.42.0.1`), because reporting one would mute the fault just as surely as recording one would. One thing the change nearly broke and now pins: `DIAG_LAST_IP_PATH=""` is a privacy **disable**, not a fall-back, and a suppression that only silenced the *file* would have become a leak the moment the address came from somewhere else — so the disable is checked before the live read runs, and a test asserts the live read is never even called.
- **The handoff rescue timer now re-checks instead of firing once and giving up** (litclock-dev#676). When setup finishes but the PWA handoff never does — control_server crashed, or nobody opened the app — `litclock-handoff-fallback` writes `.handoff-complete` so the clock is not stuck on a splash forever. (It cannot rescue a device whose setup never completed at all: the service requires `.setup-complete` to be present, which is the same requirement that produced this bug.) It fired **once**, ten minutes after boot, and on the devices it exists for it usually fired too early to do anything — then never came back. The service requires `.setup-complete` to be *present*, and on a fresh or cloned card that appears only when the recipient finishes entering their WiFi password, which `first-boot.sh` allows up to 1800 seconds for. A recipient who takes longer than ten minutes over unboxing, finding the hotspot, the captive sheet, picking a network and typing a password got the single shot fired into an unmet condition — and nothing re-arms it: nothing outside the `systemctl enable` line touches the unit, and `first-boot.sh` never restarts it, so `OnActiveSec` never re-bases either. Ten minutes is not a generous allowance for the target user; our own QA budgets ~30s just for the WiFi join plus IP-geo. The safety net was absent for precisely the population it is for, and the visible failure is a clock sitting on "Ready to read." indefinitely whose only exit is a power cycle. The comment calling the single fire deliberate reasoned that "once `.handoff-complete` exists the service's `ConditionPathExists` makes it a no-op" — true of a device that is already set up, which is the one population this timer is *not* for. The load-bearing question was whether a **condition-skipped** oneshot still re-arms `OnUnitActiveSec` — if it does not, the cadence ends at the first skip and nothing is fixed. That was settled by measurement rather than by reading: on systemd 255, a throwaway unit mirroring this one's two conditions took 8 consecutive skipped firings, each of which re-armed the timer; the service then ran on the very next tick after the condition became true, and setting the negative condition returned it to skipping with the cadence unbroken. `litclock-bootcheck.timer` is corroboration only, and a weaker one than it first appears — it uses the same three keys with different values, and its gate on this marker is the *opposite* polarity, so its fleet history evidences a succeeding oneshot re-arming, which was never in doubt. The cadence deliberately does **not** become a retry that eventually gives up: the script keeps refusing while the timezone is unknown, forever, with no attempt counter, because a wrong-time clock arrived at slowly is still the outcome design-review A2 forbids. A test asserts the script gains no countdown.
  Making it recurring turns it into a **live writer** of `.handoff-complete`, so `reset-setup.sh` and `prepare-for-cloning.sh` now stop it before they clear the markers. The window was already closed — both scripts remove `.setup-complete` first, and the timer needs that present *and* `.handoff-complete` absent — but that ordering is now load-bearing for a second reason, so it is pinned by a test rather than left as a comment, and the writer is in the stop list on its own merits (litclock-dev#673's lesson was to stop the writers first and verify, not to depend on an ordering staying correct). Two notes for whoever reads the journal: a device stuck with an unknown timezone now logs one refusal line every ten minutes — about 144 lines a day against a 64 MB cap with 7-day retention, which is noise-free arithmetic and is exactly the abnormal state an operator wants a record of — and `update.sh` now re-arms this one timer after `daemon-reload`. That last part is not cosmetic: `daemon-reload` does **not** re-arm a timer that has already elapsed — it keeps `NextElapse=infinity` — and the unit loop starts only timers a run *newly enables*, which this one never is, since pi-gen enables it. Measured both ways: reload alone gave 0 firings in 15s at a 5s cadence, a restart resumed it immediately. Without it, a device that takes an OTA while sitting in the handoff window would not get the cadence until its next boot — and that window is exactly the population the cadence is for. The re-arm is guarded on the unit being enabled, so it cannot undo an operator's opt-out, and deliberately not generalised to every timer: restarting `litclock.timer` mid-update could drop a minute's render, and restarting `litclock-update.timer` from inside `litclock-update.service` is a job-ordering hazard.
- **An update landing mid-setup no longer starts the clock on a timezone nobody has confirmed** (litclock-dev#675). `.handoff-complete` is the marker that lets quotes start, and design-review A2's rule binds every automatic writer of it: *a clock that paints at the WRONG time is worse than no clock*. `control_server/handoff.py` and `scripts/litclock-handoff-fallback.sh` both refuse when the timezone is unknown; `update.sh` did not. Its reasoning was that `.setup-complete` had been confirmed, "so this device is past first-boot" — which is false precisely during the handoff window, the window **defined** as `.setup-complete` present and `.handoff-complete` absent. It is reachable rather than theoretical: the PWA is up during that window and `routes/updates.py` has no handoff gate, and `litclock-update.timer` is `Persistent=true` with a stamp clone prep does not clear. Before litclock-dev#673 cloned cards shipped with `.handoff-complete` already present, so this branch was a no-op on every clone; now clones sit in the same window fresh flashes always have, which puts the gift path in scope. The visible failure is not a stopped clock, it is a **confidently wrong** one — on a clone, painting on the *gifter's* timezone, since clone prep does not reset `/etc/localtime` either.
  The guard has **two** conditions, and the second one matters as much as the first. Gating on the timezone alone would have been a brick-class regression in the other direction: a genuine pre-PR2 device with weather turned off has an empty `WEATHER_LATITUDE` and a perfectly correct timezone, and refusing to migrate it stops the quotes on a device that has been painting for months — the exact outcome this migration was written to prevent. So the refusal also requires that setup finished **recently**. A device in the handoff window wrote `.setup-complete` minutes ago (the window is bounded by the 120-second auto-complete and the ten-minute fallback timer); a pre-PR2 device wrote it when it was first provisioned. A clone cannot fake that, because `prepare-for-cloning.sh` removes the marker and the recipient's own first-boot writes a fresh one — a test pins that, since the whole design rests on it. `update.sh` also now announces itself with the same `handoff: completed via …` string the other paths use (litclock-dev#646): it is another completion path, journald is the only diagnostic channel on the device, and an operator greps one string to learn how a handoff completed.
- **A cloned SD card no longer paints quotes over the recipient's setup screen** (litclock-dev#673). `prepare-for-cloning.sh` removed `/etc/litclock/.setup-complete` but never `.handoff-complete`, while `reset-setup.sh` has cleared both since EPIC litclock-dev#383 PR2. `litclock.service` is gated on the handoff marker (`ConditionPathExists`), so a prepared master — and therefore **every card cloned from it** — shipped with the quote gate already satisfied by the previous owner's marker. Measured on the v0.224.0 RC bench pass: the clock started 12s after boot, *during* the recipient's setup, and started again before the first had finished, giving roughly seven minutes of blocked render at 3.1s CPU — contending for the panel rather than computing. The same image on a genuinely fresh flash logs `skipped because of an unmet condition check` until the operator taps Done; the stale marker was the only difference. On that run the setup splash happened to win the display, but which one wins is a race, and this is the cloning path, the highest-fanout channel the project documents. **Review found the one-line fix was not sufficient on its own**: both markers are re-creatable, and clone prep cleared them with their writers still running. The PWA rewrites `.handoff-complete` via `sudo touch` on the Done tap and on any Settings save, and `update.sh` re-touches it as its PR2 migration step — a run that had already passed the `.setup-complete` check keeps going for minutes and reinstates the marker near the end, silently, after this script has printed "SD Card Ready for Cloning!". That is the same shape litclock-dev#660 closed by powering the Pi off. Clone prep now stops `litclock-control.service` and the update unit *before* clearing, which is the order `reset-setup.sh` has always used. The guard is derived rather than restated: it reads every positive `ConditionPathExists`/`Assert*` gate out of the shipped unit files and asserts both reset paths clear all of them, so a new gate added to any unit fails the suite until both scripts handle it — and it executes the real removal step against a temporary config dir, because the first version of it passed with the fix commented out.
- **A freshly provisioned clock no longer greets its new owner with a false "Connection issue"** (litclock-dev#645). Every clock coming out of first-boot showed **Something needs attention → Network: Connection issue** with a blank LAN IP in the PWA, starting about five minutes after setup and clearing only at the next DHCP renewal — up to an hour on a 7200s lease. Nothing was wrong with the device: `nmcli` had a valid address, and the e-ink handoff splash printed that address correctly on the same screen the owner had just scanned. Only the diagnostics view disagreed, because it does not ask NetworkManager — it reads `/run/litclock/last-rendered-ip`, which the NM dispatcher writes. The dispatcher was gated on `.handoff-complete` at the top of the script, above both of its bookkeeping writes, and the ordering on a fresh provision is fixed and always this way round: wlan0 comes up on the owner's network *before* the handoff marker is written, so the single `up` event that would have recorded the address was always the one skipped. The grey "Not yet collected" tier would normally mute a section with no data, but it requires an empty SSID on the reasoning that SSID-present-with-no-IP is a real DHCP failure — an inference that is wrong by construction here, since the collected marker sat behind the *same* gate while the SSID was populated. So the section rendered as a fault, and the 300s settling grace expired long before the marker could appear. The gate now sits immediately above the render it was written for: recording the current IP and refreshing the collected marker are inert bookkeeping and happen on every event, while `litclock.service` stays suppressed during hotspot teardown exactly as before. Events that changed something now say so in the journal instead of exiting silently — the silence is what let this sit unnoticed; a repeat event for an unchanged address stays quiet on purpose, since that is the common case and the journal is small. **Pre-existing, not a regression**; visible on every first run since the dispatcher shipped. **Suppressing a false alarm must not suppress a true one**, and un-gating the write opened exactly that door, so the dispatcher now refuses to record an address that would lie: its own setup hotspot gateway (wlan0 carries `10.42.0.1` during first-boot, and that is not the clock's LAN address), and a `169.254.x` link-local — the likely case, not the exotic one, since that is what NetworkManager self-assigns when DHCP fails on the owner's network. The anomaly check treats *any* non-empty value as a healthy network, so recording either would have meant a clock that never got a lease reporting itself fine, forever, on the very path this fix targets. The two QR producers already rejected those ranges before encoding a URL; the dispatcher was the one "LAN IP" producer that did not, and it is the one diagnostics reads. Also from review: the run directory is created with its ownership spelled out rather than a bare `mkdir` (root-owned `/run/litclock` would silently break every pi-side writer for the rest of that boot), and the previous address is read bounded and whitespace-stripped before being logged, because it lives in a pi-writable directory and is re-emitted by root — unbounded it could fail the log call large enough to abort the script before the render, and unstripped a planted newline could forge a standalone dispatcher line in the journal. The old tests asserted the gate's *text*, which the bug never touched, so the new coverage runs the real script against a rewritten path tree and asserts behaviour on both sides of the gate, with every guard mutation-checked to confirm it can actually fail.
- **The journal no longer reports the wrong reason a clock finished setup** (litclock-dev#646). The handoff completes by any of four paths — tapping **Done — Start the Clock**, saving a setting, the browser-timezone fallback, or the 120s timer — and only the timer logged anything. Worse, it logged unconditionally on expiry: the function it checked returns "complete" for the already-complete case too, so the timer announced `auto-completed after 120s timeout` for handoffs the Done button had finished minutes earlier. Three bench cycles on `dev-20260815-b0c0590`, three misattributions — the marker's mtime was untouched by the timer every time, so it demonstrably did no work; it just claimed it. The third cycle is the clearest: it completed by saving a setting, which logged nothing at all, so the journal's *only* record of that handoff was the false one, with nothing to contrast it against. This cost real time during QA, where the checklist asks for all three completion paths to be verified separately: establishing that a Done tap had actually completed one cycle meant ignoring the journal and doing marker-mtime arithmetic against the phase-entry timestamp. On a device where journald is the only diagnostic channel, a line asserting a false cause is worse than no line. Attribution now happens at the moment the marker changes state rather than at each caller, which makes a false claim structurally hard: every path names itself, a trigger arriving after the handoff already completed says so instead of taking credit, and the timer still reports honestly in both directions — it names itself when it genuinely completed the handoff, and says it fired and found the work done when it did not. A settings save *after* the handoff window stays silent, since every save for the life of the device passes through that branch and would bury the one line that matters. Review turned up three more holes in the same shape, all closed: the marker write was a check-then-create, so two triggers racing produced one marker and **two** completion claims naming different paths — the same defect reached by another route, and the loser also moved the marker's timestamp, which is the evidence that overturned the original misattribution in the first place; it is one atomic create now, so exactly one caller can claim it. The one completion line a Pi actually emits was the one with no test behind it, because `/etc/litclock` is root-owned and every test ran against a writable temp directory, so the whole fix was covered only on a path the device never takes. And the last-resort fallback completer — the path that runs precisely when the control server is broken — announced itself in wording nobody would grep for, so an operator checking a rescued clock would have concluded the handoff never happened, which is the same wrong conclusion this entry is about.

### Security

- **Cards prepared for cloning now ship with SSH off, like every other handoff** (#57, the last dev-side piece of litclock-dev#657). `reset-setup.sh` disables SSH on both of its terminal handoff arms; `prepare-for-cloning.sh` — the *highest-fanout* handoff there is, "Creating SD Cards for Friends & Family" — contained zero occurrences of `ssh`, so whatever posture the master held was frozen into the image and every clone of it. And the operator preparing masters is typically doing so over SSH, which is precisely the state that got captured. The gate now runs on the poweroff arm, last thing before the power-off, after the fail-closed password check — an aborted prep leaves the operator their remote access, the same ordering rule as reset-setup's arms — and its function body is byte-identical to reset-setup's (and so to public's), pinned against the litclock-dev#708 golden fixture so three copies cannot become three truths. Two interactions did the real design work: disabling sshd kills the operator's own session, and dying there would skip the poweroff whose absence re-mints the setup key on the next boot (litclock-dev#660) — so the tail ignores SIGHUP for exactly the [gate, marker, poweroff] window, after printing the full summary plus an explicit "this session will drop" warning while anyone can still read it — and the trap alone is NOT enough, which a real-pty reproduction proved: once sshd dies the script's stdout is a closed pty, every echo fails with EIO, and under `set -e` the first echo after the drop (the gate's own "done") killed the script before the marker retired or poweroff ran, so on any session that may drop the tail's output is redirected to /dev/null after the warning (deliberately not the journal, which Step 5 just vacuumed), while a local console keeps every line; and a gate that *refuses* the handoff (port 22 verified still open) now exits with the litclock-dev#701 unfinished-run marker still in place, because that refusal is invisible over a dropped session and the marker is how the next, console, run finds out. `--no-poweroff` — the inspection path — deliberately keeps SSH and says in yellow that the imaged card will carry the master's posture. Recovery on a clone is the standard one: a blank `ssh` file in the SD boot partition. Executed tests cover both arms and the refusal path; six mutants killed, including the gate moved off its arm and a one-character drift from the golden.
- **The SSH handoff gate now exists on dev too, and behaves identically on both repos** (litclock-dev#657, litclock-dev#528). `reset-setup.sh`'s `disable_ssh_for_handoff` — which leaves a device being passed on in the SSH posture a recipient would get from a fresh flash, off — existed **only on public**, authored there as a deliberate divergence because the bench wanted SSH to survive a factory reset. That left no dev-first path for any fix that has to call it, which is what blocked #57 (clone prep is the higher-fanout handoff and had no SSH posture at all). The function and its header comment are now here **byte-identical to public's**, verified by diffing the two, and a test fails if they ever drift. **The dev exception was considered and dropped** (owner, 2026-08-20): it was first shipped as an `/etc/litclock/.dev-image` marker written by pi-gen, and the reason it existed does not survive contact with how easy recovery actually is — a blank `ssh` file in the SD card's boot partition re-enables SSH at the next boot, and the bench Pi has a monitor. A divergence that buys a convenience already available two other ways is not worth the drift that made this issue necessary, so the marker, its pi-gen writer and a build-workflow variable all went with it. The practical consequence is recorded where it bites, which review showed was four places rather than one: CLAUDE.md's check 3 is a before/after comparison **across** resets and cannot follow "run SSH work first", so it now says to run that block from the console or restore access between sub-steps; `docs/recovery.md` no longer promises SSH survives until you disable it; `docs/script-reference.md` did not even list `--poweroff`, let alone its SSH consequence; and the script's own `--help` now names both arms and the way back in, because a gate whose consequence is undocumented reads as a fault the first time someone meets it. Also from review: the test that lifts and RUNS the gate was executing its real `rm -f /boot/ssh …` — harmless as an ordinary user, but under `sudo pytest` or on a Pi it would delete the operator's own recovery flags — and the guard against the exception coming back was a blacklist of the three names just deleted, so any new name walked past it in CI. It is structural now: nothing may run before the disable.
- **The setup hotspot's password no longer travels as a command-line argument** (litclock-dev#654). `sudo` writes the full argv of every command it runs to syslog, and the flashed image sets journald `Storage=persistent`, so `nmcli device wifi hotspot … password <psk>` wrote the setup key onto the SD card. Clone prep's `--vacuum-time=1d` could not be relied on to remove it — the natural workflow is provision a card, verify it, then prepare it for cloning, which is squarely inside that window — and every clone of that card carried the key. litclock-dev#620 closed the read side (support-bundle redaction); this closes the write. **The fix the issue proposed does not work, and fails silently.** Measured on the bench Pi (NM 1.42.4): `nmcli --ask device wifi hotspot …` with the password piped on stdin returns 0, reports success, and stores a key **nmcli generated itself** — `--ask` prompts for missing *required* arguments, and hotspot's `password` is optional, so the prompt never fires and stdin is discarded. Shipping it would have put a password on the e-ink that does not open the network, on the path every new device takes. The profile is therefore built explicitly and the secret rides the connection editor's stdin, the same channel the litclock-dev#613 PSK restore already uses, with a read-back that refuses to raise an AP whose stored key differs from what the panel will print. The property set was derived by **diffing a profile built the old way against the new one on hardware**, so it is that command's own output rather than a guess; the WPA2/CCMP triple in particular is load-bearing, since `key-mgmt wpa-psk` alone would also permit WPA/TKIP. Verified end to end on the bench Pi: AP up in mode `ap`, SSID on air, `10.42.0.1`, NM's dnsmasq reading the captive-portal config directory, stored key equal to the intended one — and the audited argv now reads `add` / `modify` / `edit` / read-back / `up` with no password token anywhere, against a journal that still holds the old form's leak from the run immediately before it. - **Support-bundle redaction: one more argv path closed, and three ways it was damaging the lines it did touch** (litclock-dev#661). The bundle is the artifact users attach to GitHub issues, so both halves matter — what leaks out, and whether what is left can still be read. **The leak**: `_redact_nmcli_argv` early-returns on any line without `nmcli`, so the long-option form was untouched entirely, and `scripts/first-boot.sh` passes the now-permanent setup key that way (`--hotspot-password AbC12dEf`) — putting it in world-readable `/proc/<pid>/cmdline` for the provisioning window and in sudo's command-audit line. Low practical severity, since the same password is on the e-ink panel in plaintext by design and the only local accounts are `pi` and `root`, but it is the same space-separated-argv class litclock-dev#620 set out to close, left open on the sibling path. Long options now redact regardless of the command, and need no line-scope guard: `--password` is unambiguous in a way the bare word never is. **The damage**: a passphrase containing a space was only *partially* redacted (`password ***REDACTED*** secret pass'`), which is worse than none because it makes the leak look handled — WPA2 permits spaces and our own validator accepts them. A quoted-value alternation was tried first and rejected on review, because it cannot be made safe against the quoting a real log line contains: an embedded apostrophe matches `'Bob'` and leaves `s secret pass'`, and an unterminated quote falls through to the bare-token branch and leaves `secret`. The nmcli form now takes the rest of the line, which has no such edge — and costs almost nothing, because nmcli takes the credential as its LAST key/value pair, so the SSID and every other argument precede it and are kept. The `nmcli -s -g <property> connection show uuid …` read form, which this repo runs at three sites on the litclock-dev#613/litclock-dev#616 PSK-snapshot paths, had its **subcommand** redacted rather than a value: `-g` takes a field list, so the token after the property name is `connection`, not a secret. No key was ever at risk there (the value comes back on stdout, not argv) — the filter was simply erasing which command ran, on the paths hardest to debug remotely and the ones a bundle is most often pulled for. And every keyed redaction not at line start ate the character before the key, because the delimiter was matched *outside* the captured prefix: `export PSK=x` came back as `exportPSK=***REDACTED***`, `--hotspot-password=` as `--hotspotpassword=`. Also widened the line-scope guard to match whole tokens including nmcli's accepted abbreviations — `nmcli d w connect MyNet password …` passed through completely unredacted, unreachable from our own code but not from an operator's SSH session, which sudo logs verbatim. Tokenising tightens the guard at the same time, since `connection` no longer matches inside prose. Every one of these is now pinned by a test that was verified red without its fix, including the line-scope guard itself, which previously could be deleted outright with all six existing tests still green.

- **A test now pins that every file `update.sh` chmods is already tracked executable** (litclock-dev#682). Phase 6 runs `chmod +x "$INSTALL_DIR"/scripts/*.sh`. If git records one of those files non-executable, that chmod is a real mode change on every update: Phase 2's `git reset --hard` overwrites the mode-only dirt exactly as the warning promises, and then Phase 6 of the **same run** re-creates it, so the tree is dirty again before the run ends and the next update warns the operator about changes the previous one made. Nothing breaks — the cost is that `[WARN] Uncommitted changes detected` is exactly the line that should make an operator stop and look if they had really hand-edited something on the device, and instead it fires on every update and is wrong every time, which is how a genuine warning gets trained out of usefulness. - **Releases are now cut with `scripts/cut-release.sh`, which makes the blank-update-card mistake unmakeable rather than merely detectable** (litclock-dev#687). litclock-dev#681 added a CI gate that fails a tag build when `CHANGELOG.md` has no section for the tag, and that gate stays — but it cannot prevent the defect it was written for, for two reasons. It fires **after the tag is public**: the PWA resolves updates from `/tags`, so the blank card reaches the fleet at `git push --tags`, the very event that triggers the workflow. And **the OTA path never touches the image asset** — `scripts/update.sh` applies an update with `git fetch --tags` + `git reset --hard <tag>` and never downloads the `.img`, so failing the build stops the fresh-flash artifact and has no bearing on updating at all. Together the gate protects flashing, not updating; the blank card was an updating problem. The new script puts the promotion and the tag in one step that cannot do the second without the first, and runs `check-changelog-section.py` — the same check CI runs — against its own output, so the script and the gate agree by construction rather than by convention. It refuses a dirty tree, a detached HEAD (where `git push origin <branch>` silently no-ops and would orphan the tag), a tag that already exists locally or on origin (tags are never moved: the fleet resolves updates from `/tags`, so moving one changes what already-updated devices fetched), a non-release tag shape (an RC or QA tag must not consume `[Unreleased]`), an empty `[Unreleased]` or one holding headings with no entries under them (releasing nothing is the other half of the same mistake), two `[Unreleased]` headings (promoting the wrong one would release the wrong notes, silently), `--expect-sha` not matching HEAD — which is how the operator states which commit they validated, since the methodology is validate-first-tag-last — and `--expect-sha` given a *ref name* rather than a sha, because `--expect-sha HEAD` resolves to HEAD by definition and so reads in shell history as "I pinned the commit" while checking nothing. Two more refusals came out of review: a `CHANGELOG.md` that is a **symlink** (the promotion is written with `cp`, which follows one, so the release heading landed in a file outside the repository), and **HEAD or the branch moving while the script runs** — everything above is checked against a snapshot taken before a confirmation prompt an operator can sit at indefinitely, and a concurrent checkout in that window put the commit and the tag on a commit nobody validated while the summary still printed the old sha as its contents. **It deliberately does not push.** Pushing from inside would reintroduce the "irreversible the instant it runs" property the script exists to remove, so it prints the push — atomic, and with the refs **shell-escaped** (`printf %q`), because that line is meant to be pasted into a shell and `git check-ref-format` accepts branch names like ``rel'ease``, `x$(id)` and `a;echo`; wrapping them in literal quotes is not enough, since a name containing a quote breaks straight back out — and prints how to undo everything before it. Any failure after the CHANGELOG is rewritten now rolls all the way back, including the release commit: the worst shape was a release commit that had consumed `[Unreleased]` with no tag, which made the obvious retry die with "has no entries" and left the operator stuck. The duplicate-tag probe is bounded by `timeout` (an unroutable-but-answering origin blocked for the kernel's full TCP retry window, against a comment promising that being offline must not block a release) and the script now prints which remote URL it consulted, because `origin` is not necessarily the namespace the fleet resolves from. Two further classes came out of an adversarial pass over the fixes themselves. **The rollback could destroy someone else's work**: it accepted "any commit whose parent is the commit we started from", which a concurrent writer in the same worktree satisfies, and `git reset --hard` then discarded a stranger's commit and files while the script printed "restored" — this project has a recorded incident of exactly that concurrency. It now resets only the sha its own `git commit` produced, and when it cannot roll back it says so and tells the operator not to reset blindly, rather than claiming a restoration that did not happen. And **the fleet-safety guard was consulting the wrong remote**: `origin` in this clone is the dev repo, while `update.sh` and `update_state.py` resolve releases from the public one, so re-cutting a version that had been live on the fleet for days passed both the local and the remote check. The namespace is now resolved from the same `DEFAULT_OWNER`/`DEFAULT_REPO` constants the device uses and every remote that could be it is probed, with a loud warning when none matches. The same finding surfaced a second fleet-class hazard with no guard at all: both resolvers pick the **highest** semver rather than the newest tag, so a single typo'd high version — `v0.324.0` for `v0.234.0` — permanently hides every release numbered below it, and the "tags are never moved" doctrine forbids the only remedy. A release must now be the immediate successor of the highest tag that exists anywhere, local or remote, with `--allow-version-jump` as the deliberate escape. `git add` also grew a guard: a held `.git/index.lock` used to exit with git's raw error and no rollback, and the restore now works from a byte snapshot rather than `git checkout --`, which needs the very lock that was the problem. Finally, a bug the tests could not have caught and running the script against **this repository** did: the "is there anything to release" check piped into `grep -q`, which exits at the first match and closes the pipe — the producer takes SIGPIPE and, under `set -o pipefail`, the *pipeline* reports 141 even though the match was found. The failure is size-dependent, so all 99 tests passed on their few-line fixtures while the real CHANGELOG, whose entries run to thousands of characters, filled the 64 KiB pipe buffer and made the script report `'## [Unreleased]' has no entries` — refusing to cut any release at all. It now uses a herestring, and the two other early-exit pipelines were converted the same way. Review then caught the regression test repeating the original mistake: the synthetic fixture was ~43 KB, *under* the pipe buffer, so it passed against the restored bug and only the real-CHANGELOG case actually discriminated. It is now several times the buffer and asserts its own size, so it cannot silently shrink back under the threshold. The structural guard was also a substring scan that `|grep -qE`, `| grep -E -q` and `| grep --quiet` all walked straight past; it matches the pipeline *shape* now.

  The tests execute the script against throwaway repositories rather than grepping its source — including a deterministic drive of the HEAD-moves-mid-run race, by stubbing the CI gate the script shells out to so it perturbs the repository inside exactly that window, with no sleeps and no background process, and a concurrent-writer `pre-commit` hook standing in for the shared-worktree incident. A third adversarial pass, aimed at the newest code, found that the remote match was a suffix glob with no host check and no boundary before the owner — it accepted `github.com.evil.test/<owner>/<repo>`, a nested `archive/<owner>/<repo>` path and `not<owner>/<repo>`, while missing a trailing slash or a differently-cased owner — and that the constant extraction matched `DEFAULT_OWNER_BACKUP` as readily as `DEFAULT_OWNER`. Both are now exact: host, owner and repo are compared as identities, case-insensitively, against the remote's *configured* URL (`git remote -v` prints the `insteadOf`-rewritten one). ### Changed

- **The PWA's Factory reset now clears the setup-WiFi key, which it had been keeping** (litclock-dev#660). litclock-dev#620 made that key permanent and rotated it in gift mode and `prepare-for-cloning.sh`, but not on the path `litclock-reset.service` runs for the PWA's **Factory reset** card: `reset-setup.sh --wipe-wifi --strict-env-wipe --poweroff --yes`. Because that wipes WiFi, the next power-on comes up in the setup hotspot — broadcasting `LitClock-Setup` with the PREVIOUS owner's key, permanently, surviving every reset the new owner later performed, while the card's own copy promised "Erases **everything** — all settings and WiFi". **v0.223.0 had no such leak**, because the key regenerated every provisioning cycle, so this was a regression litclock-dev#620 introduced rather than a pre-existing gap. **The discriminator is `--wipe-wifi`, not the power-off.** A hand-run `sudo reset-setup.sh --poweroff` does not wipe WiFi: the clock powers off, boots straight back onto its saved network, and never raises a hotspot at all — so there is no setup network for a stale key to protect, and rotating would strand the owner's phone for nothing. Android's WiFi error surfaces have changed materially across releases, so both readings are recorded rather than one replacing the other, and the strongest version of the original argument — that Android left no user-discoverable recovery short of Forget This Network — is treated as unproven. None of that changes the decision: a stable per-device password means a normal owner never reaches any of these screens, which is the right outcome however gracefully a given Android build degrades. The password is now read-or-created once from `/var/lib/litclock/hotspot-password` (0600, atomic write) and reused, so the name and the credential stay in lockstep. Persistence is best-effort by design: an unreadable, malformed or unwritable file regenerates and logs, because provisioning must never be blocked by its own bookkeeping, a symlink or FIFO planted at that path is refused rather than followed or blocked on, a pre-existing world-readable file is tightened to 0600 on read, and the write is fsynced so a power cut during provisioning cannot lose a password a phone has already saved. **Gift mode regenerates it**, and so does `prepare-for-cloning.sh` — without that, every SD card cloned from one prepared master would broadcast `LitClock-Setup` with the same permanent key. ### Fixed

- **A clock that cannot get an IP address no longer repaints the panel on every retry** (litclock-dev#667). litclock-dev#645 taught the NetworkManager dispatcher to treat a `169.254.x` self-assigned address as no address at all, so it could not mute the missing-IP fault — correct, but it blanked the variable the same-IP short-circuit is gated on. A blanked address failed that gate, never reached the early exit, and fell through to a full e-ink render, so **every** `dhcp4-change` reaching the dispatcher without a usable address queued another `litclock.service` start: three renders measured for three identical events where a real address produces one. That is precisely the unbounded-render failure the litclock-dev#309 review guard was written to prevent — each render holds the SPI bus, blocks the legitimate minute-tick paint, and spends panel cycles a device with no UPS and a finite budget cannot get back. **The same hole was open one branch over**: when the interface has no IPv4 at all the address is empty rather than blanked, and it repainted on all four of four events measured in the test harness. **Bench QA afterwards showed both branches are narrower in the field than that framing suggests** — see the reachability note at the end of this entry. The fix separates two questions that had been sharing one variable: *have I already acted on this address* (the observed value, kept before blanking, in its own tmpfs marker) and *what address should diagnostics believe* (the blanked value, still the only thing written where `read_lan_ip` can see it). Every repeat now coalesces — real, link-local, or nothing at all — while the first event after losing **or regaining** a routable address still repaints, because in both directions the panel is showing a QR that no longer matches reality. Because that early exit now sits above the address write, it additionally proves the diagnostics marker already agrees before skipping: without that, a plain file planted at the coalescing path in the pi-writable `/run/litclock` could suppress the write for the life of the boot and resurrect litclock-dev#645's false "Connection issue" with every symlink guard intact, and an ordinary deletion of the marker would never self-heal. Three smaller defects in the same file went with it: the change log line read `wlan0 IP changed to unknown (was: none)` on a blanked event while the marker still held the real prior address — a line asserting a change that did not happen and reporting "none" for a value that exists, on a device where journald is the only diagnostic channel; `install -d -o pi -g pi` failed **wholesale** where the `mkdir -p` it replaced would still have created the directory, so on any install whose user is not literally `pi` the marker write silently no-opped for the whole boot; and the two run-dir creation sites had drifted apart, leaving the one that runs on a permanently-DHCP-broken clock — the only one that runs there — without the pi-ownership attempt at all. The guard that should have caught the render storm asserted only that the address was not recorded and never looked at whether anything rendered. **Reachability, established on hardware after the fix landed and recorded here rather than left to imply more than it should:** on a single-stack IPv4 network a DHCP failure produces *no dispatcher invocations at all* — NetworkManager cycles `ip-config → failed → disconnected → prepare` and never reaches `activated`, so no `up` event fires and `dhcp4-change` needs a lease that never exists. The link-local branch likewise does not arise on its own, since nothing here sets `ipv4.link-local` and NM's default is to fail IPv4 rather than self-assign. Both branches were reproduced only by forcing the interface state directly. The empty branch is genuinely reachable where `ipv4.may-fail=yes` (it is) **and** IPv6 works, letting a connection activate v6-only with no IPv4 — a dual-stack network with broken v4 DHCP. The fix is correct and the coalescing is verified on hardware for the reachable case; the render storm is simply rarer in the field than the harness measurements alone would suggest. A related gap the same pass found — the last-rendered-ip marker is never cleared, so a stale address mutes the missing-IP anomaly for the whole outage — is tracked as litclock-dev#672 and is pre-existing, not introduced here.

Review also caught that the check the step calls "the real gate" could miss a survivor: `-e` follows symlinks and is false for a dangling one, so a failed unlink of a dangling symlink at the password path reported success. The invariant is that no entry survives there — a surviving entry means the removal did not do what it claimed, whatever it points at — so the check now tests `-L` too. ## [v0.219.0] - 2026-07-13

### Fixed
- **A freshly provisioned clock no longer greets its new owner with a false "Connection issue"** (litclock-dev#645). Every clock coming out of first-boot showed **Something needs attention → Network: Connection issue** with a blank LAN IP in the PWA, starting about five minutes after setup and clearing only at the next DHCP renewal — up to an hour on a 7200s lease. Nothing was wrong with the device: `nmcli` had a valid address, and the e-ink handoff splash printed that address correctly on the same screen the owner had just scanned. Only the diagnostics view disagreed, because it does not ask NetworkManager — it reads `/run/litclock/last-rendered-ip`, which the NM dispatcher writes. The dispatcher was gated on `.handoff-complete` at the top of the script, above both of its bookkeeping writes, and the ordering on a fresh provision is fixed and always this way round: wlan0 comes up on the owner's network *before* the handoff marker is written, so the single `up` event that would have recorded the address was always the one skipped. The grey "Not yet collected" tier would normally mute a section with no data, but it requires an empty SSID on the reasoning that SSID-present-with-no-IP is a real DHCP failure — an inference that is wrong by construction here, since the collected marker sat behind the *same* gate while the SSID was populated. So the section rendered as a fault, and the 300s settling grace expired long before the marker could appear. The gate now sits immediately above the render it was written for: recording the current IP and refreshing the collected marker are inert bookkeeping and happen on every event, while `litclock.service` stays suppressed during hotspot teardown exactly as before. Events that changed something now say so in the journal instead of exiting silently — the silence is what let this sit unnoticed; a repeat event for an unchanged address stays quiet on purpose, since that is the common case and the journal is small. **Pre-existing, not a regression**; visible on every first run since the dispatcher shipped. **Suppressing a false alarm must not suppress a true one**, and un-gating the write opened exactly that door, so the dispatcher now refuses to record an address that would lie: its own setup hotspot gateway (wlan0 carries `10.42.0.1` during first-boot, and that is not the clock's LAN address), and a `169.254.x` link-local — the likely case, not the exotic one, since that is what NetworkManager self-assigns when DHCP fails on the owner's network. The anomaly check treats *any* non-empty value as a healthy network, so recording either would have meant a clock that never got a lease reporting itself fine, forever, on the very path this fix targets. The two QR producers already rejected those ranges before encoding a URL; the dispatcher was the one "LAN IP" producer that did not, and it is the one diagnostics reads. Also from review: the run directory is created with its ownership spelled out rather than a bare `mkdir` (root-owned `/run/litclock` would silently break every pi-side writer for the rest of that boot), and the previous address is read bounded and whitespace-stripped before being logged, because it lives in a pi-writable directory and is re-emitted by root — unbounded it could fail the log call large enough to abort the script before the render, and unstripped a planted newline could forge a standalone dispatcher line in the journal. The old tests asserted the gate's *text*, which the bug never touched, so the new coverage runs the real script against a rewritten path tree and asserts behaviour on both sides of the gate, with every guard mutation-checked to confirm it can actually fail.
- **The journal no longer reports the wrong reason a clock finished setup** (litclock-dev#646). The handoff completes by any of four paths — tapping **Done — Start the Clock**, saving a setting, the browser-timezone fallback, or the 120s timer — and only the timer logged anything. Worse, it logged unconditionally on expiry: the function it checked returns "complete" for the already-complete case too, so the timer announced `auto-completed after 120s timeout` for handoffs the Done button had finished minutes earlier. Three bench cycles on `dev-20260815-b0c0590`, three misattributions — the marker's mtime was untouched by the timer every time, so it demonstrably did no work; it just claimed it. The third cycle is the clearest: it completed by saving a setting, which logged nothing at all, so the journal's *only* record of that handoff was the false one, with nothing to contrast it against. This cost real time during QA, where the checklist asks for all three completion paths to be verified separately: establishing that a Done tap had actually completed one cycle meant ignoring the journal and doing marker-mtime arithmetic against the phase-entry timestamp. On a device where journald is the only diagnostic channel, a line asserting a false cause is worse than no line. Attribution now happens at the moment the marker changes state rather than at each caller, which makes a false claim structurally hard: every path names itself, a trigger arriving after the handoff already completed says so instead of taking credit, and the timer still reports honestly in both directions — it names itself when it genuinely completed the handoff, and says it fired and found the work done when it did not. A settings save *after* the handoff window stays silent, since every save for the life of the device passes through that branch and would bury the one line that matters. Review turned up three more holes in the same shape, all closed: the marker write was a check-then-create, so two triggers racing produced one marker and **two** completion claims naming different paths — the same defect reached by another route, and the loser also moved the marker's timestamp, which is the evidence that overturned the original misattribution in the first place; it is one atomic create now, so exactly one caller can claim it. The one completion line a Pi actually emits was the one with no test behind it, because `/etc/litclock` is root-owned and every test ran against a writable temp directory, so the whole fix was covered only on a path the device never takes. And the last-resort fallback completer — the path that runs precisely when the control server is broken — announced itself in wording nobody would grep for, so an operator checking a rescued clock would have concluded the handoff never happened, which is the same wrong conclusion this entry is about.

### Added
- **Diagnostics: a "Download full logs" export for shell-less support** (litclock-dev#416 follow-up). The Control PWA's diagnostics "Copy support payload" already hands a helper the system state + a **3-line** journal preview per unit — deliberately shallow so it never blocks first paint. That's often too thin to actually debug a failing unit. New `GET /api/diagnostics/support-logs` assembles a single downloadable `text/plain` bundle: the same redacted system payload plus a **~50-line** journal tail per unit across the `DIAG_UNITS` allowlist, so a non-technical owner can hand over one file (or paste) that carries enough context — no SSH. Off the page/poll critical path; deep reads use a **distinct, line-count-scoped cache key** so they never serve or poison the 3-line page-preview cache; a wall-clock budget bounds the serial `journalctl` loop and appends an explicit *named-units* truncation note rather than silently dropping units; `no-store` + redacted (secrets in journal lines are stripped). The existing per-unit `GET /api/diagnostics/journal` also gained a capped `?lines=N` param (default 3, max 200) for pulling a deeper tail for a single unit. Surfaced as a plain `<a download>` link beside the Copy button, so it works with no JavaScript.

- **LKG auto-revert: the clock now self-heals a bad over-the-air update without SSH or an SD reflash** (litclock-dev#209 follow-up). litclock-dev#209 shipped the *writer* (`litclock-lkg.service` records the last SHA that actually painted to `/var/lib/litclock/lkg-sha`, heartbeat-gated); this ships the *consumer*, `litclock-bootcheck.service`. It answers one question per boot — "did the clock paint a frame since this boot?" — via the tmpfs render heartbeat (network-independent, so a merely-offline clock is never touched). On a persistent failure it self-heals: fail 1 and 2 auto-reboot to retry (a single failed render may be transient), and on fail 3 it pins the last-known-good SHA and routes recovery **back through `update.sh`** in a new rollback mode, which does the *complete* install (git + submodules + venv hash-gate + units→`/etc` + sudoers + dispatcher + smoke) rather than a partial `git reset` — so a dependency- or unit-level bad update is actually recoverable, not just a code-only one. If the recovered code also fails it gives up (a persistent `bootcheck-gave-up` marker + best-effort "please re-flash" splash) instead of looping, bounding the whole sequence to ~4 reboots. Two supporting fixes make the recovery target reliable: `update.sh` **no longer clears `lkg-sha`** at the start of an update (the heartbeat-gated writer replaces it only once new code paints, so `lkg-sha` always points at the last code that actually rendered — a dead-on-arrival update can never blank the recovery target, closing the DOA gap), and a `blocked-sha` suppression stops the weekly timer from re-installing the exact release bootcheck just reverted from until a newer release supersedes it. Runs as `pi` using only the `systemctl reboot` + `systemctl start --no-block litclock-update.service` grants already in `sudoers/020_litclock-control` — no new privilege, works after litclock-dev#387 drops `010`. Hard prerequisite for litclock-dev#82 (public release: SSH is off, so a recipient's bricked clock would otherwise need a physical reflash). Design reshaped in `/plan-eng-review` + Codex outside-voice (plan: `docs/plans/lkg-bootcheck-plan.md`).

### Security
- **Closed the pi→root escalation paths so dropping the blanket `010_pi-nopasswd` sudo is safe** (litclock-dev#387, prerequisite for litclock-dev#82). Each was harmless while `010` grants `pi` NOPASSWD:ALL, but becomes a live hole the moment the public image ships with only the scoped `020_litclock-control` allowlist. **(tz-wrapper)** `geocoding.set_system_timezone` (the IP-geo + A18 browser-tz fallback) ran `sudo timedatectl set-timezone <arbitrary-tz>`, which `020` could only authorize via a `set-timezone *` glob — a hole letting `pi` set the clock to any string reaching the resolver. It now calls a new root-owned wrapper `/usr/local/lib/litclock/litclock-set-timezone` that re-validates the timezone against the kernel zoneinfo list *in root-owned code* (a metachar pre-filter + `grep -Fxq`, and `timedatectl` resolved via PATH — never an env-var binary override that could cross `sudo`); `020` authorizes just that fixed path. **(C1)** the root NetworkManager dispatcher invoked the **pi-writable** `/home/pi/litclock/scripts/litclock-mark-collected.sh` — pi→root on the next DHCP event once `010` drops. It now runs a root-owned copy in `/usr/local/lib/litclock/` (no fallback to the repo copy). **(prepare-for-gift)** `litclock-prepare-for-gift.service` (root, startable by `pi` via `020`) exec'd the **pi-writable** `reset-setup.sh` — pi could edit it and get arbitrary root code. It now execs a root-owned copy (with its sourced `lib/state.sh` shipped root-owned alongside), and the gift-message step runs the root-owned system `/usr/bin/python3` instead of the pi-writable venv interpreter. **(NTP grant)** `first-boot.sh`/`install.sh` run `sudo timedatectl set-ntp true`, which `020` didn't authorize — a fresh clock would silently never sync time once `010` drops; added as a fixed-argv grant. **(C2)** the dispatcher + mark-collected writer run as root but write into the `0755 pi pi` `/run/litclock` and `/var/lib/litclock` dirs; both now refuse to follow a symlink at the target and stage via `mktemp` (O_EXCL) instead of a guessable `$MARKER.tmp.$$` path. (A residual sub-millisecond check-then-open race remains — closing it fully needs an `O_NOFOLLOW` open POSIX `sh` can't express — accepted as an explicit risk: it requires an already-compromised `pi` shell winning a race for a limited-content root write.) All root-owned helpers install root:root across pi-gen, `install.sh`, and `update.sh`; the gift-mode `timedatectl set-timezone UTC` fixed-argv path is unchanged.

- **Diagnostics redaction now rounds compound-key and odd-shaped coordinates in the support-logs / journal export** (litclock-dev#497, litclock-dev#498). The diagnostics redaction rounds coordinates to ~city-block precision so the copy / support-logs / journal surfaces stay safe to paste into a public GitHub issue — but `_COORD_KEYED_RE` led with `\b`, which cannot match inside a compound key (the `_` before `LATITUDE` is a word char, so there is no boundary). systemd logs `env.sh` verbatim when a line uses `export` (`Ignoring invalid environment assignment 'export WEATHER_LATITUDE=33.1234'`), so the device's **full-precision, street-level home coordinates** rode un-rounded into the exported bundle while the structured field correctly showed the rounded `33.12`. The lead-in is now a zero-width negative lookbehind (`(?<![A-Za-z])`) — matching how the sibling `_PSK_RE` handles compound keys — which fixes the compound key, *also* catches back-to-back coordinates with no separator (a consuming lead-in would eat the boundary char, leaving nothing for the next coord's lead-in), and is safer against false positives (a *letter* before the keyword still blocks `belong=` / `along=` / `flat=` / `translation=`). The value group additionally rounds signed and scientific-notation spellings and JSON quoted-key forms (`{"lat": …}`); comma-decimals are deliberately left un-matched, since the `_validate_latitude` writer's `float()` rejects them (so they are unreachable) and a comma is ambiguous with a list separator (`lat=1,2,3` must never be fabricated into a coordinate). Found via a coordination-protocol pentest of the Control PWA (blind executor + blind validator, then a Codex adversarial `/review`); every non-plain-decimal shape was verified non-reachable in-tree, so the value-shape work is defense-in-depth. No incremental LAN exposure — the PWA is unauthenticated on the LAN by design and already serves coordinates rounded by default; the real fix is the share-safety contract (exported support-logs are meant to be safe to post publicly).

- **Weather response cache moved off the SD card onto tmpfs** (litclock-dev#434). ### Fixed
- **Fresh-flash clock never left the "Ready to read." handoff splash** (litclock-dev#388, litclock-dev#484). On a freshly imaged Pi the clock got stuck on the handoff splash forever: handoff itself completed fine (marker written, location + timezone resolved), but `litclock.service` (the per-minute quote painter) died every minute with lgpio `'GPIO busy'` so no quote ever painted. Root cause: `control_server` (`litclock-control.service`) is **long-lived** and painted the handoff splash **in its own process** — and the lgpio line claims a paint makes are held for the whole process lifetime (`epd.sleep()` only deep-sleeps the panel; `module_exit()`/gpiozero-close does not free the claims — only process exit does). So the always-on PWA held the e-ink GPIO forever and the quote painter could never claim it. (authorclock never hit this because its control_server had been restarted post-setup, freeing the GPIO; only a pristine fresh flash exposes it.) The splash now paints via a **short-lived subprocess** (the same pattern `first-boot.sh` already uses for the hotspot/status splashes) that claims, paints, and frees the lines on exit — `render_eink_splash` no longer touches the hardware in-process. A cross-model `/review` hardened two follow-ups: the `handoff-splash` CLI now exits non-zero on a failed paint (so a real display fault surfaces instead of a silent success), and the timeout handler no longer logs the subprocess argv (which carried the SSID + location name) into the diagnostics log.
- **On-screen setup copy no longer names "Safari"** (litclock-dev#482, litclock-dev#485). The e-ink hotspot/setup splash (`"Or open Safari:"`) and the iOS captive-portal bridge page (`"Open in Safari"`) hard-coded the iOS browser name, which is wrong on Android / any non-iOS phone. Both now say "browser" generically; the bridge instruction was rephrased to not quote a specific button label at all (iOS's actual captive-assistant escape button is labelled "Open in Safari", so a quoted "Open in Browser" would misdescribe the only control that page is shown to). Found in fresh-flash test-Pi QA.
- **iOS captive portal now auto-opens on a fresh flash** (litclock-dev#483, litclock-dev#489). Fresh-flash test-Pi QA (with the litclock-dev#486 `CAPTIVE-PROBE` diagnostic in the image) pinned the real cause from the hotspot's dnsmasq log: iOS 17+ sends an HTTPS-RR (type 65) query for `captive.apple.com` before the A query (RFC 9460), and NetworkManager's shared-mode dnsmasq — which reads `/etc/resolv.conf` and inherits a public upstream like `8.8.8.8` — **forwarded** that type-65 query upstream. The isolated hotspot has no route to that upstream, so the forward failed and dnsmasq returned `REFUSED (EDE: network error)`, which iOS reads as hostile DNS and silently demotes the captive sheet (the exact failure litclock-dev#178 was chasing). The `local=/#/` mitigation never actually stopped the forward — it only looked fine on client Pis whose inherited upstream happened to be reachable and answered NODATA. The fix adds **`no-resolv`** to the captive dnsmasq config so it keeps no upstream at all and answers every non-A type authoritatively as NODATA; iOS falls through to the A record and pops the sheet. Manual "open in your browser" always worked (it only needs the A record), which had masked the DNS cause. Reproduced + fix-verified against a standalone dnsmasq 2.90 with an unreachable upstream (type-65 REFUSED → NODATA).
- **First-boot hardening for the captive-portal window** (litclock-dev#483, litclock-dev#488). Shipped alongside litclock-dev#489 from the same investigation; useful defense-in-depth even though the DNS forward above (not readiness) turned out to be the actual cause. (1) `first-boot.sh` now waits for the setup server to be listening on port 8080 (bash `/dev/tcp` poll, 25s cap, best-effort) **before** painting the hotspot QR, so the user's join always lands after the server can answer a probe. (2) The image build now **ships pre-compiled bytecode** for `src/` (`compileall --invalidation-mode checked-hash`, compiled with the runtime venv interpreter, then chowned to `pi`) instead of deleting all `__pycache__` in the finalize stage, so a fresh flash no longer compiles the setup path cold on its first run; `checked-hash` keeps the image reproducible and correct across `update.sh`. A cross-model `/review` caught that the compile runs as root after the build's `chown` (would have shipped root-owned `.pyc` the `pi` runtime couldn't refresh after an OTA) — closed with a re-chown.

### Security
- **control_server now sends `X-Content-Type-Options: nosniff` + `X-Frame-Options: DENY` on every response** (litclock-dev#477). Added off the back of a whole-codebase SAST + DAST pass (report: `docs/security-sast-dast-2026-07.md`), which found the code otherwise clean — 0 dependency CVEs (pip-audit + npm audit), no SSRF (fixed hosts, quoted queries), no command injection (fixed-argv `sudo`/`systemctl`; the diagnostics `unit` arg is allowlist-gated), and CSPRNG (`secrets`) for the WiFi hotspot password + CSRF + confirm tokens — but the PWA served no HTTP hardening headers. `nosniff` is universal defense-in-depth; `X-Frame-Options: DENY` closes a clickjacking vector, since the PWA is unauthenticated on the LAN and a malicious same-LAN page could otherwise iframe it and trick the owner into a state-changing control (Reset WiFi / power off). Deliberately **not** applied to `setup_server` — the first-boot captive portal may render inside an OS captive-portal WebView, which `DENY` would break. A content-security-policy is deferred to the remote-exposure tripwire (where auth + HTTPS + CSP all become required together).

### For contributors
- **`setup_server` background threads are now joined between tests, killing a `test_wifi_retry_flow` CI flake** (litclock-dev#478, litclock-dev#479, litclock-dev#480). The WiFi connect/teardown handlers spawn daemon threads (`_delayed` SIGTERM timer, `_connect_and_teardown`, `_resolve_and_signal`) that write module globals + call test-monkeypatched functions. `reset_state()` (the litclock-dev#355 isolation helper) previously only polled the `WIFI_CONNECT_IN_FLIGHT` flag — which `_delayed`/`_resolve_and_signal` never set — so a prior test's thread could outlive its case and fire its (now next-test-monkeypatched) `os.kill`/retry into the next test's counters (intermittent `assert 4 == 3` / `assert 1 == 0` failures in CI while passing in isolation). It now tracks every spawned thread via a `_spawn_bg` registry and **joins** them (`start()` inside the lock to avoid a join-before-start `RuntimeError`; a keep-alive filter so a thread that outruns the join budget isn't forgotten), and `_delayed` uses a cancellable `_BG_CANCEL.wait(delay)` so `reset_state` cancels the timer without firing a real SIGTERM (conftest reverts `os.kill` before the reset fixture runs, so a fired signal would kill the runner). Regression tests assert on their own thread handle, not the shared registry count, so they can't re-introduce cross-test coupling. A post-merge cross-model `/review` of the first cut caught two latent races that the follow-up hardened.
- **Captive-portal probes now log Host + path + User-Agent in provisioning mode** (litclock-dev#483, litclock-dev#486). The setup server's access log recorded only the request line + status, which couldn't pin why an iOS phone's captive-portal sheet sometimes doesn't auto-open on join (observed in fresh-flash QA; tapping the browser manually always worked). A provisioning-only `CAPTIVE-PROBE` diagnostic now logs which host/path/UA each probe hit — paired with dnsmasq's already-enabled `log-queries`, a phone-join repro captures the full DNS→HTTP probe path so the root cause is pinnable. Diagnostic only; no change to the captive-portal response flow. Investigation (litclock-dev#483) confirmed the server side is correct (iOS probes get the non-"Success" 200 CNA bridge), so the miss is iOS-side probe timing/behavior — still open pending the repro logs.

### Changed

### Fixed
- **Settings auto-save controls can no longer persist state opposite the UI under rapid taps** (litclock-dev#457, with the litclock-dev#458 helper convergence). All three auto-save controls (Weather toggle, Temperature pill, Advanced toggles) used to `abort()` the in-flight `fetch` on a re-tap — but an aborted request whose POST already reached the Pi still completed its `env.sh` write, and writes serialize on the flock by acquisition order, not send order, so an older save could land *after* a newer one and persist the opposite of what the toggle showed (until the next reload). The fix is client-side **serialization + coalescing**: each control now keeps at most one save in flight and coalesces rapid taps to the latest desired value, firing a single follow-up save only after the in-flight one settles. Because two saves for one control never overlap, the flock can't reorder them — persisted state always converges to the value the user landed on (a burst of N taps costs ≤2 round-trips). On failure the helper reverts to the last server-confirmed value and alerts. As part of the same change (litclock-dev#458) the Weather toggle and Temperature pill moved off their hand-rolled `AbortController` handlers onto two shared helpers — `wireBooleanToggleAutoSave` (checkboxes) and the new `wireSegmentedAutoSave` (segmented pill) — so all four auto-save controls share two code paths instead of four near-identical bodies (~120 lines of duplication removed). Known residuals (all self-heal on reload): genuinely simultaneous edits from two *different* devices stay last-flock-wins, and a response lost *after* the server commits can't be reconciled client-side — full convergence would need server read-back, the reconcile alternative litclock-dev#457 weighed and set aside. Cross-model `/review` (Codex GPT-5.5 + testing/maintainability/adversarial Claude subagents) confirmed the fix and the no-reintroduced-F2 invariant; added `settings.weather-toggle.test.js` (the toggle had zero JS coverage) plus serialization/coalescing + revert-to-confirmed coverage for both helpers.
- **Oneshot service rows no longer read warning-ochre while the section pill reads OK** (litclock-dev#449, follow-up to litclock-dev#443). litclock-dev#443 stopped a `DIAG_ONESHOT_UNITS` member (`litclock.service`) mid-paint in `activating`/`deactivating` from tripping the services anomaly — the section header pill correctly reads **OK** in that ~2–5 s per-minute window. But the per-unit *row* state chip stayed warning-ochre (the `.diag-service__state--activating`/`--deactivating` CSS), so a user expanding the Services drawer at that instant saw an ochre `activating` chip on `litclock.service` under an OK section header — a small but real visual contradiction (exposed, not introduced, by litclock-dev#443: before it the ochre matched the anomaly). `_build_service_states` now emits a `state_modifier` per row that drives the chip *color* while the chip *text* stays the literal systemd state: a oneshot caught in `activating`/`deactivating` gets the neutral graphite `transient-ok` tone (matching the OK section tone), while non-oneshot `activating`/`deactivating` and any `failed` keep the warning-ochre tint they should. The oneshot carve-out is now a single shared predicate, `_is_oneshot_nonanomaly(unit, state)`, referenced by all three consumers (`_compute_anomalies` verdict, `_is_obviously_healthy` lazy-tail gate, and the row tone) so they can't drift.
- **Oneshot `litclock.service` lifecycle no longer false-positives the oxblood "Clock isn't running" banner** (litclock-dev#443). `litclock.service` is `Type=oneshot` and cycles `inactive → activating → active → inactive` in 2–5 s during every per-minute quote paint. A `/diagnostics` poll landing in the `activating`/`deactivating` window (~5–8 % of page loads by sample-rate math) tripped the services anomaly, which escalates the banner to its highest-severity error tier — "Clock isn't running." — even though the clock was *literally rendering the next quote at that second*. The oneshot carve-out in `routes/diagnostics/_anomalies.py::_compute_anomalies` now skips `activating`/`deactivating` for `DIAG_ONESHOT_UNITS` members alongside `inactive`; `_is_obviously_healthy` in `_collectors.py` is updated in lockstep so the litclock-dev#433 lazy-tail filter also treats the normal oneshot lifecycle as healthy (no needless journal fork). `failed` still trips for oneshots (a real failure), and non-oneshot units (e.g. `litclock-control.service`) get no lifecycle pass. A genuinely wedged paint stuck in `activating` still surfaces — via the `last-quote` anomaly once `picked_at` ages past 90 s (covered by a regression test). Pre-existing since litclock-dev#416; surfaced by the v0.214.4 grey-tier work making `/diagnostics` a maintained support surface (caught during authorclock hardware QA 2026-06-13).

- **Shutdown splash now paints reliably even when reboot lands mid-render** (litclock-dev#271). `litclock-shutdown.service` now declares `Before=litclock.service` so the farewell-splash `ExecStop` only fires once any in-flight per-minute render has stopped and released the SPI/GPIO bus. Previously, a reboot issued within ~9s of a minute tick raced the timer-fired render and `epd.init()` failed with `'GPIO busy'` on roughly 1 in 7 shutdowns, leaving the previous literary quote frozen on the e-ink across the reboot instead of the "Restarting…" / "Powered Off" frame. (Codex pre-merge review caught a draft using `Conflicts=litclock.service` — that would have fired the shutdown splash on every per-minute clock render because `Conflicts=` is bidirectional. Pinned by a regression test.)
- **Weather "Show on display" toggle now auto-saves on tap** (litclock-dev#346). Tapping the toggle persists the new state immediately — no more reverting to last-saved on tab switch if you forgot to tap Save. City/zip still require Save (only the toggle is special-cased because its iOS-style visual implies instant persistence). Concurrent rapid taps cancel each other via AbortController so the final state always matches your last tap.
- **Updates tab phase progression no longer briefly regresses** (litclock-dev#345). The reading-list visual no longer momentarily flips backward from phase 2 to phase 1 mid-update. The pre-existing page-load probe was racing with `fireApply` — its late-arriving snapshot would replay an older phase index over the live progression. The probe now early-returns if a reading-list is already showing, deferring to whichever code path got there first.
- **Status tab "Last update" row no longer em-dashes when a cold-boot update races NTP sync** (litclock-dev#342 I2). The validate-then-cp gate that gates `/var/lib/litclock/last-update.json` writes was rejecting any timestamp older than 60 seconds — but Pi Zero 2W has no real-time clock, so a fresh-boot update fired before chrony settled would stamp pre-1970 times, fail the gate, and silently drop the persist write. Window widened to 3600s; the gate's intent ("not torn / not stale-from-a-previous-run") still holds.
- **Updates tab no longer freezes mid-update** (litclock-dev#329). The phase reading-list used to stick on "Updating Python packages" for 30-60s when `litclock-control.service` restarted mid-Phase-7 and a single poll dropped. Now the list optimistically ticks all 7 phases to complete and enters reconnect mode the moment any poll fails after an update is in flight — so you always see honest progress, not a stuck spinner. **Also (litclock-dev#342 I10):** when you navigate back to /updates while an update is already in flight (another tab kicked it off, or the weekly timer fired), the reading-list now keeps polling forward instead of freezing at whichever phase the page-load snapshot showed.
- **Settings → Weather → "Clear" link** (litclock-dev#325). Once a city is set, the "Currently: …" hint now carries an explicit "Clear" affordance. Tapping it removes the city name, latitude, and longitude in one shot. Weather pauses until you set a new location. Renders for any user with at least one of the three weather location keys populated (covers fresh-install coord-only setups too).
- **Destructive actions no longer burn the confirm token when they fail** (litclock-dev#328). If Restart, Power off, Reset WiFi, Prepare-for-Gifting, or Apply Update fails server-side (missing systemd unit, sudoers issue, busy gate), retrying with the same modal now shows the real underlying error instead of the misleading "Confirm token is missing, expired, or already used." Caught in M8 hardware QA when litclock-dev#327's missing units first surfaced.
- **Status tab "Last update" row survives reboots in the post-update window** (litclock-dev#334). `update.sh` now writes `/var/lib/litclock/last-update.json` at the end of every successful update — a persistent fallback when the tmpfs `update.status` clears or a graceful-offline exit deletes `lkg-sha`. The row reads the freshest available source (live tmpfs → persistent snapshot → LKG SHA mtime → em-dash for true first-run state).
- **Status tab works under old service-worker-cached HTML** (litclock-dev#335). Android PWA users whose service worker is still serving HTML cached from before the previous release no longer see a silently-frozen "Last update" row. `status.js` falls back to setting the parent element when the new child hooks aren't found, so the row populates with the combined `"<sha7>, N min ago"` string under either layout.
- **`/api/status` and `/api/update/status` won't OOM or hang on malformed state files** (litclock-dev#336). Both endpoints now use a shared bounded reader: open with `O_NOFOLLOW | O_CLOEXEC | O_NONBLOCK`, validate the file is a regular file via `fstat` on the opened FD, cap size (8KB for JSON, 64B for SHA), reject FIFOs/symlinks/directories. Defensive hardening against same-user attackers or accidental corruption.
- `scripts/update.sh` no longer `systemctl restart`s `litclock-shutdown.service` in Phase 7 (litclock-dev#331). The unit is a stop-hook (Type=oneshot, ExecStop=shutdown-splash.sh), so `restart` fired the stop half mid-update and painted "Powered Off" on the e-ink for ~11s while the Pi was happily mid-pip — alarming UX, and a real risk a user would unplug the Pi mid-install. The unit has no runtime state worth restarting; unit-file changes are already picked up at Phase 5 daemon-reload. Removes ~11s from total update time as a bonus.
- Status tab "Last update" row no longer shows `—` right after a successful update (litclock-dev#330). The route was querying `systemctl show -p ActiveEnterTimestamp litclock-update.service`, but the PWA-triggered apply path doesn't reliably populate that property — so the row went silent in exactly the post-update moment the user most wants the trust signal. Now reads `/run/litclock/update.status`'s `finished_at_unix` + `to_version` (state=complete), falling back to `/var/lib/litclock/lkg-sha`'s mtime + sha7 across reboots; renders em-dash only when neither file exists (true first-run state).

### For contributors
- **`test_setup_server` tests no longer flake under specific pytest orderings** (litclock-dev#355). `setup_server.py` holds `WIFI_CONNECT_ERROR` and `WIFI_CONNECT_IN_FLIGHT` as module-level globals, written asynchronously by the `_connect_and_teardown` daemon thread. The previous `monkeypatch.setattr` fixture snapshot-restored values around each test, but a late write from a prior test's still-running thread became monkeypatch's "original" for the next test — so `test_wifi_success_signals_and_shuts_down` could see `WIFI_CONNECT_IN_FLIGHT=True` from a sibling test and fail intermittently. New `setup_server.reset_state(wait_for_inflight=2.0)` helper drains the in-flight thread under `_WIFI_CONNECT_LOCK` before zeroing connect-flow globals + scan cache; an autouse `tests/conftest.py` fixture invokes it before and after every test. The fixture catches `ModuleNotFoundError` only (not the broader `ImportError`) so a real top-level import bug in `setup_server.py` surfaces loudly instead of silently disabling test isolation. Contract pinned by `TestResetState` including a thread-based test that asserts late writes don't leak past the drain barrier. Caught on PR litclock-dev#353 CI run 25968703096; preexisting `os.kill(SIGTERM)` race noted as P3 follow-up litclock-dev#364.
- **Python deps now use a `pip-compile`'d lockfile** (litclock-dev#323). `requirements.in` is the human-edited source of truth for direct pins; `requirements.txt` is the **generated** lockfile with every transitive (werkzeug, click, itsdangerous, blinker, markupsafe, cffi, pycparser, h3, flatbuffers, numpy) explicitly pinned. Closes the eager-strategy gap from litclock-dev#321: PR litclock-dev#322 narrowed `update.sh` to plain `--upgrade` (no eager) to avoid silent fleet-wide transitive bumps killing Flask, but that left transitive security fixes unreachable. The lock-at-release-cut workflow restores deterministic install AND a controlled bump path — maintainer runs `pip-compile --upgrade requirements.in` locally, reviews diff, tests on a Pi, tags release. All 8 existing `requirements.txt` readers (update.sh, install.sh, pi-gen, lint.yml, 3 tests, README/CONTRIBUTING) keep working unchanged — same filename, same `name==version` line format. `requirements-apt.txt` filter still strips the 5 apt-provisioned names (gpiozero/lgpio/spidev/pigpio/colorzero) at install time. See CONTRIBUTING.md → "Updating Python dependencies" for the full workflow.
- **`MAX_RELEASE_NOTES_BYTES = 4096`** in `update_state.py` caps `release_notes` before `write_cache` so the cached JSON stays under `MAX_GH_API_CACHE_BYTES`. Without the cap, a verbose CHANGELOG could exceed the read-side limit and cause `/api/update/check` to refetch GitHub on every request, burning the PAT rate budget. **Important pairing:** `write_cache` now uses `json.dump(..., ensure_ascii=False)` — the default ASCII escaping inflates each non-ASCII codepoint to `\uXXXX` (6 bytes), so a 4KB emoji-heavy notes section would otherwise serialise to ~12KB and trip the read gate. Pattern: if you ever cap a string by UTF-8 byte length, the writer that produces the consuming file MUST also write UTF-8 (not ASCII-escaped) for the cap to be meaningful.
- **`scripts/update.sh` persist function now sweeps orphan `.tmp.*` siblings** on entry (litclock-dev#342 I4). Mirrors the manifest-sweep pattern from PR litclock-dev#293. Defensive: if a prior persist died between staging and mv (disk full, OOM, kill -9), the .tmp.\<pid\> sibling lingered indefinitely.
- **`ConfirmTokenStore.restore()` now clamps `expires_at_monotonic` to `<= now + TTL_SECONDS`** (litclock-dev#342 I8). Defense-in-depth — today's callers always round-trip the expiry from `consume()` so the clamp is a no-op on the happy path. A future refactor that synthesises an expiry (e.g. hardcoding `now + 86400`) can no longer silently mint a long-lived token bypassing the 300s TTL contract.
- **`prepare_for_gift`'s `CalledProcessError` branch narrows the staged-message unlink to `returncode in (4, 5)`** (litclock-dev#342 I9). Per `man systemctl(1)`: 4 = unit not found (the litclock-dev#327 install-gap motivation), 5 = unit not loaded / masked. Other returncodes preserve the staged message so the unit can read it if it dispatched anyway (the narrow dbus-glitch window the existing comments already acknowledged for the token-restore path). The original unconditional unlink risked silently replacing a user's personalized welcome with the default splash on the rare dispatch-but-non-zero-exit race.
- New shared `safe_read_json` / `safe_read_text` helpers in `src/control_server/update_state.py` close a TOCTOU window when reading state files. Pattern: `os.open(path, O_RDONLY | O_NOFOLLOW | O_CLOEXEC | O_NONBLOCK)` → `fstat` the resulting FD → `S_ISREG` + size check → `read`. The `O_NONBLOCK` matters specifically for FIFO defense — without it, `open()` on a malicious FIFO hangs the worker thread, defeating the hardening. Use these helpers (not raw `Path.stat()` + `open()`) for any new defensive file-read in the project.
- `scripts/update.sh` now wraps its body in `flock -n -E 75 /var/lib/litclock/update.lock` so concurrent manual invocations exit cleanly with a clear message instead of racing on the state files. Best-effort fallback when the lock file can't be created (sandbox/CI environments where `/var/lib/litclock` doesn't yet exist) logs `log_warn` so the journal records the degraded mode.
- `ConfirmTokenStore.consume()` signature changed from `-> bool` to `-> float | None` (returns the original monotonic expiry on success). New `restore(action, token, expires_at_monotonic)` method atomically re-adds the token; route handlers call it on any pre-side-effect failure path. `TimeoutExpired` deliberately does NOT restore (paranoid: systemd may have dispatched).
- `_validate_latitude` / `_validate_longitude` now accept empty string as a valid "unset" state — required for the Clear weather path to work. Routes enforce all-or-none across the three weather location keys at the API layer to prevent incoherent partial-coord saves via direct JSON callers.
- `create_app` defaults now seed `UPDATE_STATUS_FILE`, `LAST_UPDATE_FILE`, and `LKG_SHA_FILE` from their `LITCLOCK_*_FILE` env vars at app-creation time, matching the existing `ENV_FILE` pattern. Future tests using `app.config[...] = tmp_path` see consistent behavior; future tests that set env vars after import no longer silently use production paths.
- `.settings-button--secondary` now matches DESIGN.md "Buttons" Secondary spec (transparent bg + `--accent` text + `--accent` border, hover/active to `--accent-muted`). Prior implementation read as a disabled grey chip and didn't map to any DESIGN.md variant. All future non-destructive secondary actions in Settings should reuse this class.
- All `CalledProcessError` branches in the 5 destructive route handlers (reboot, poweroff, prepare_for_gift, update_apply, wifi_reset) now carry an inline comment acknowledging the residual dbus-race dispatch window. Future destructive actions that are NOT idempotent at the systemd level must narrow the restore to specific pre-dispatch stderr patterns or remove the restore for that action.

**Hardware-found platform limit (2026-04-30, post-merge Android QA):** the SW machinery is **inert on the v1 plain-HTTP origin** for both platforms, not just iOS. Per W3C spec, only `localhost` / `127.0.0.0/8` / `[::1]` are "potentially trustworthy" in plain HTTP. `192.168.x.x` is not, so both iOS Safari AND Android Chrome report `isSecureContext = false` and refuse to register the SW. The original M6 hardware probe only tested iPhone; Android was assumed from spec docs and turned out to be wrong. Net effect: cached-shell-during-reboot, offline rendering, and Android PWA-install all DON'T work today. The wiring ships intact (sw.js Flask route, manifest endpoint, sw-register.js feature-detect, 11 SW-specific tests) because (a) the visible M6 wins — cold-launch splash, fonts, AtHS hint, Dynamic Type — all work without SW, and (b) the wiring activates unmodified when v2 cloud-relay TLS lands. Full discussion in `docs/control-pwa-platform-limits.md`.

### Control PWA — M3 Settings tab (litclock-dev#245)

Edit your LitClock from a phone-pinnable web app, no SSH needed. Open the Settings tab on `litclock.local:8443`, change weather city, units, gift-mode message, or NSFW filter — taps land on the e-ink display within ~3 seconds, not 60. Five sections (Weather / Units / Gift Mode / Location / Advanced), no-JS forms work in any browser, JS-enabled flows get a live geocode preview as you type a city or zip.

**Under the hood:**
- `setup_server.save_settings` and the new control_server now share one writer (`config.atomic_update`), one validator, one lockfile. The first-boot flow and the post-boot Settings tab can no longer disagree about how `env.sh` gets written.
- Free-form values (gift-mode message, resolved location name) are wrapped via `shlex.quote()` at write time and content-allowlisted (no backtick, no `$`, 280-char cap on gift mode).
- Server-side geocoding via Nominatim with IP-country biasing — type "78701" and you get Austin, TX, not a foreign postal code. Timezone updates automatically when coords change.
- CSRF protection via reflexive Origin/Referer match against `request.host` (works for `litclock.local`, raw IP, or whatever name your LAN's mDNS resolves first) plus a multi-use synchronizer token (action=settings, TTL 30 min).
- New env keys: `WEATHER_ENABLED`, `WEATHER_LOCATION_NAME`, `GIFT_MODE_ENABLED`, `GIFT_MODE_MESSAGE`. The first-boot flow keeps writing the existing keys; new keys default to safe values until edited.
- `litclock.service` is `Type=oneshot` + timer-fired, so saves don't restart anything — they fire `systemctl start --no-block litclock.service` for one immediate tick. The minute-tick contract stays intact.

**Gift-mode runtime semantics** (rendering the message in place of a quote on the e-ink) is deferred to a follow-up issue. M3 ships the editing surface only.

### Heads-up — weekly auto-update behavior (litclock-dev#209)

LitClock now updates itself automatically **once a week on Sunday at 03:00 local time** (with up to 7 days of randomization to avoid everyone hitting GitHub at once). The appliance posture is deliberate: non-technical users should never have to think about updates, and power users can opt out in one command.

**What the weekly update does:**
- Pulls the latest blessed GitHub Release (`litclock-*` tag), not `origin/master`. A release is only cut once a SHA has been hardware-verified.
- Rebuilds the Python venv when `requirements.txt` changes.
- Runs a post-rebuild **smoke test** (`python -m src.literary_clock --dry-run`). If the render fails, the update auto-reverts to the previous SHA and the clock keeps ticking on the old code.
- Records a last-known-good SHA to `/var/lib/litclock/lkg-sha` after the clock has run 10 minutes on the new code (observability today; an opt-in auto-revert on repeated boot failures is a future issue).
- Merges new env-var names from `env.sh.sample` into your `env.sh` without overwriting your values.

**What does NOT update automatically:**
- OS packages (`apt upgrade`), Pi firmware — those need A/B partitioning we don't have yet.

**How to opt out:**
```bash
sudo systemctl disable --now litclock-update.timer
```

**How to inspect:**
```bash
systemctl status litclock-update.timer
journalctl -u litclock-update.service --since "1 week ago"
```

See the [Updating](README.md#updating) section of the README for the full story. Refs litclock-dev#209.

#### Auto-update — Added
- `scripts/lib/github_api.sh` — shared GitHub REST API helpers (auth, timeout, graceful-offline). Used by `update.sh` and `download_images.sh`.
- `resolve_target_sha()` in `scripts/update.sh` — resolves the latest non-prerelease Release tag to an authoritative SHA via `git rev-list`. Reads `tag_name` (not the unreliable `target_commitish`).
- Phase 4.5 smoke-test block in `update.sh` — runs `python -m src.literary_clock --dry-run` between venv rebuild and systemd unit sync, auto-reverts on failure, writes `/var/lib/litclock/update-failed` (cleared on next successful update).
- `--dry-run` flag on `src/literary_clock.py` — renders a quote to an in-memory PIL image without touching GPIO/SPI. Used by the update smoke test.
- Subtle "!" glyph in the top-right corner of the clock face when the last auto-update failed. Self-clearing.
- `systemd/litclock-update.service` + `.timer` — weekly oneshot with `TimeoutStartSec=120`, `OnCalendar=Sun 03:00`, `Persistent=true`, `RandomizedDelaySec=7d`.
- `systemd/litclock-lkg.service` + `scripts/litclock-lkg-record.sh` — LKG heartbeat writer. Records HEAD SHA after 10 minutes of clean clock runtime. Writer-only in v1; auto-revert consumer deferred (see `TODOS.md`).

#### Auto-update — Changed
- `scripts/download_images.sh` routes all GitHub API fetches through `lib/github_api.sh`. Behavior preserved.
- `.github/workflows/build-image.yml` — tag-push `gh release create` now passes `--target ${{ github.sha }}` so `target_commitish` carries a real SHA rather than `"master"`.
- `scripts/install.sh` and `pi-gen/stage3/03-install-services/` — auto-enable the new update timer + LKG service at install/image-bake time.
